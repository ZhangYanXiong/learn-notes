## 核心概念速查

| 概念 | 一句话定义 | 不等于什么 |
| --- | --- | --- |
| User Intent | 用户用自然语言或业务事件表达的原始意图 | 可直接执行的 Goal |
| Goal | 目标结果、范围、约束、交付物和成功标准 | 执行步骤 |
| Plan | 根据 Goal 与 State 组织 Subgoal 的可变执行方案 | Goal 或工具调用清单 |
| Subgoal | 可独立完成和验证的局部结果 | 某一个固定工具 |
| Loop | 根据环境反馈动态选择下一步的局部执行循环 | 无限 `while` |
| Graph | 描述阶段、路由、循环、并行、暂停和状态迁移的控制结构 | 多 Agent 本身 |
| Runtime | 实际调度执行、持久化和恢复任务的运行系统 | 完整 Harness |
| Harness | 模型与真实世界之间的执行、安全和反馈外壳 | 模型能力本身 |
| Context | 某次模型调用临时构造的相关工作集 | 长期存储或完整历史 |
| State | 应用维护的结构化任务事实和控制信息 | Prompt |
| RAG | 按当前问题检索外部知识 | 长期记忆 |
| Memory | 经策略管理、可修改和删除的跨会话信息 | 自动累积的聊天记录 |
| Tool | 查询或改变外部系统的能力 | 连接协议 |
| MCP | AI 应用发现、读取和调用外部能力的连接协议 | 何时调用的编排策略 |
| A2A | 独立 Agent 间发现能力、交换消息、跟踪任务和交付产物的协议 | Graph 的全局编排或业务授权 |

## 一个案例如何穿过各层

用户说：“帮我看看订单接口为什么慢，只做诊断。”

```text
Goal Intake → 补充服务、环境、时间范围和只读约束
Goal        → 找出最可能原因；至少两类证据；不得修改生产
Plan        → 确认症状 → 形成假设 → 验证原因 → 输出结论
Graph       → 诊断 → 必要时追问/审批 → 报告 → 结束
Loop        → 查指标 → 读结果 → 查日志 → 更新假设 → 验证
Harness     → 限制只读工具、步数、预算、超时，记录 Trace 和 checkpoint
```

同一个案例在不同文档中只展开该层职责，避免每篇重复整套系统。可运行的简化版本见[只读诊断案例](<../质量与实践/examples/read_only_diagnosis/README.md>)。

## 文档维护规则

1. 先确定知识归属，再增加内容；跨层内容在其他文档只保留摘要和链接。
2. 稳定概念与时效内容分开；产品能力和市场生态使用前核对官方资料。
3. 完整代码放入 Engineering 文档或示例目录；概念文档聚焦解释与边界。
4. 修改概念边界、文件名或标题时，同步检查 README、知识点索引和所有相对链接。
5. 文档更新日期只表示内容更新时间，不代表外部框架或产品仍是最新状态。
