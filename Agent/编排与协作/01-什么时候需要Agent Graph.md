## 一页结论

1. **Agent Graph 是带状态的执行图。**节点可以是模型、普通代码、RAG、工具或人工审批；边负责顺序、分支、循环和并行；运行时负责持久化、恢复与调度。
2. **它不等于多 Agent。**第一个版本通常应采用"单 Agent + 显式流程图 + 确定性工具 + 人工审批"。只有知识、权限、上下文或并行执行确实需要隔离时，才拆成多 Agent。
3. **模型负责模糊判断，程序守住确定性。**语义理解、信息归纳和动态规划可以交给模型；金额计算、权限判断、库存扣减、交易提交必须由代码和业务系统负责。
4. **最适合的任务**同时具有非结构化输入、多步骤分支、跨系统动作、长任务恢复、审批审计或专业分工。
5. **不应替代**单次模型调用、简单 RAG、固定 BPM/RPA、高频低延迟交易系统和不可验证的高风险决策。
6. **生产关键不在 Demo。**真正决定能否上线的是状态设计、工具权限、幂等、检查点、退出条件、全链路观测、真实评测集和回滚机制。
7. **用户只需表达自然目标。**Goal Intake 应结合页面与会话上下文、业务默认值、安全策略和只读工具完成目标规范化与拆分；只有高影响且无法安全推断的歧义才询问用户。
8. **Plan 由 Goal 和当前 State 派生，但不是 Goal 的组成部分。**Goal 定义终点、边界和成功标准，应该相对稳定；Plan 组织子目标、依赖和执行路线，可以随着环境反馈进行版本化重规划。

# 第一部分：心智模型

> 核心结论：Agent Graph 的价值不是增加更多 Agent，而是把模型的不确定判断放进一个可控制、可恢复、可审计的业务执行图中。

## 一、从单次调用到 Agent Graph：控制方式的演进

要理解 Agent Graph，先看它前面的几种形态各自解决什么问题、在哪里力不从心：

| 形态 | 谁决定下一步 | 状态与恢复 | 适合场景 | 局限 |
| --- | --- | --- | --- | --- |
| 单次 LLM | 应用固定调用一次 | 通常没有 | 总结、翻译、分类、抽取 | 无法处理多步骤、无业务状态 |
| RAG 问答 | 固定"检索→生成" | 通常没有业务状态 | 知识问答、文档查询 | 流程固定，无法动态分支 |
| 确定性 Workflow | 程序和规则 | 通常完整 | 审批、ETL、订单、RPA | 无法处理非结构化输入和模糊判断 |
| Tool-using Agent（Loop） | 模型选择工具 | 多为会话级 | 开放查询、个人助手 | 过程不可控、难恢复、风险动作混在推理中 |
| **Agent Graph** | **图、代码和模型共同控制** | **显式状态与 checkpoint** | **长任务、复杂分支、跨系统、高风险流程** | 建设成本高、需要工程治理配合 |

关键认识：Agent Graph 不是要取代前面的形态，而是解决它们**都覆盖不了**的那类任务——同时需要非结构化理解**和**可控执行流程**和**跨系统动作**和**故障恢复。

## 二、Agent Loop 的五个生产问题

最简单的 Agent 是一个无限循环：

```text
观察 → 模型判断 → 调用工具 → 读取结果 → 再判断 → 结束
```

它适合短任务，但企业流程会遇到：

1. **过程不可预测：**相同输入可能选择不同工具和顺序；
2. **长任务难恢复：**中间失败后只能从头开始；
3. **风险动作混在推理中：**模型可能未经批准触发写操作；
4. **上下文持续膨胀：**历史和工具结果全部进入 Prompt；
5. **难以定位问题：**无法判断错误发生在路由、检索、工具还是生成阶段。

**图式编排把控制流、状态、失败路径和权限边界显式化，让 Agent 问题重新变成可以测试和治理的软件工程问题。**

## 三、Agent Graph 是什么

把 Agent Graph 表达为一个公式：

```text
Agent Graph = Nodes + Edges + State + Runtime + Governance
```

| 组成 | 作用 | 典型内容 |
| --- | --- | --- |
| Node 节点 | 完成一项工作 | LLM、函数、RAG、API、代码沙箱、人工审批 |
| Edge 边 | 决定下一步 | 固定流转、条件路由、循环、并行、异常分支 |
| State 状态 | 保存共享事实 | 输入、中间结果、风险等级、重试次数、审批结果 |
| Runtime 运行时 | 执行和恢复 | 调度、checkpoint、暂停、恢复、并发、超时、事件流 |
| Governance 治理 | 限制风险 | 身份、权限、预算、审计、评测、终止条件 |

**注意：**Agent Graph 不一定是 DAG。追问、重试、反思和工具循环天然会形成循环，所以生产中的 Agent Graph 往往是带环状态图。

### 3.1 易混淆点：图是模型生成的，还是提前配置的？

一个常见误解是认为 Agent Graph 的图结构由模型在运行时动态生成。事实是：

> **图的拓扑（有哪些节点、节点之间有哪些可能的边）是人类架构师提前设计并配置的。模型只在预留的路由决策点上选择走哪条边，以及在节点内部做动态探索。**

以权限申请案例中的伪代码为例：

```text
graph.route("risk_check", route_by_risk,
            allowed="approve", denied="end")
```

`risk_check` 之后只能去 `approve` 或 `end`——这是提前定义的。但具体走哪条，由模型或规则在运行时判断。这就是"图、代码和模型**共同控制**"的含义：

- **图结构**（哪些节点、哪些边存在）→ 提前配置，等同于 Workflow；
- **路由选择**（走哪条边）→ 部分由模型动态判断，部分由规则确定；
- **节点内部行为**（调用什么工具、循环几次）→ 可以由模型动态决定。

### 3.2 Agent Graph 与传统 Workflow 的详细区别

因为图结构是预先设计的，Agent Graph 看起来和传统 Workflow 非常相似。下表逐维度说明二者的真正区别：

| 维度 | 传统 Workflow（BPM/RPA） | Agent Graph |
| --- | --- | --- |
| **图结构来源** | 人工设计并配置 | 同样是人工设计并配置 |
| **输入形式** | 结构化表单、固定字段 | 非结构化自然语言，需要模型抽取和理解 |
| **路由决策** | 完全由规则或字段值决定 | 部分路由可以由模型做语义判断（如意图分类、风险评估） |
| **节点内部** | 确定性代码或人工操作 | 可以包含模型调用、Tool Loop、RAG 检索等不确定性操作 |
| **是否有环** | 通常是 DAG，循环靠计数器或超时退出 | 天然支持循环（追问补信息、反思修改、重试） |
| **状态内容** | 业务字段、审批结果 | 除业务字段外，还包含模型中间产物（抽取结果、候选方案、置信度） |
| **失败处理** | 重试或人工介入 | 除重试外，模型可以动态调整策略（换查询、降级方案） |
| **适用任务** | 输入明确、规则清晰、步骤固定 | 输入模糊、需要理解和判断、但流程骨架可以预定义 |

**本质区别的一句话总结：**

> 传统 Workflow 的每个节点和每条边都是确定性的；Agent Graph 的骨架是确定性的，但在特定节点和路由点引入了模型的不确定性判断，同时用工程手段（Schema 校验、退出条件、checkpoint、人工审批）约束这种不确定性。

**什么时候选 Workflow 而不是 Agent Graph：**

- 输入已经是结构化的（表单、API 请求、数据库事件）；
- 所有分支条件都可以用字段值或规则表达；
- 不需要模型做语义理解或开放式生成；
- 已有成熟的 BPM/RPA 系统覆盖。

**什么时候需要从 Workflow 升级到 Agent Graph：**

- 输入是自然语言或非结构化文档，必须先"理解"才能处理；
- 某些路由条件无法预先枚举，需要语义分类或风险推理；
- 某些节点需要动态探索（如搜索知识库、分析日志、生成方案）；
- 流程中存在需要模型归纳、总结或创作的环节。

### 3.3 Agent Graph 相比传统 Workflow 的具体收益

既然骨架都是提前配的，为什么不直接用更成熟的 Workflow？因为 Agent Graph 在以下维度带来了 Workflow 无法实现的收益：

| 收益维度 | 传统 Workflow 的局限 | Agent Graph 如何解决 | 实际业务价值 |
| --- | --- | --- | --- |
| **接受模糊输入** | 必须由人工或前置系统把输入转为结构化字段后才能启动流程 | 模型节点直接理解自然语言、非结构化文档和图片，自动抽取所需字段 | 用户不再需要填复杂表单；邮件、聊天、文档可以直接触发流程 |
| **处理不可穷举的分支** | 每条路由必须用规则或字段值提前写死；新场景需要改流程定义 | 部分路由由模型做语义判断（意图分类、风险评估、相似度匹配） | 减少流程维护成本；新场景无需每次修改流程图 |
| **节点内动态探索** | 每个节点只能执行预定义的固定操作 | 节点内部可以运行 Tool Loop：模型决定查什么、查几次、换什么策略 | 能处理"不确定需要几步才能得到答案"的任务（如日志诊断、知识搜索） |
| **开放式生成能力** | 只能做数据搬运和规则判断，不能"创造"内容 | 模型节点可以归纳信息、生成方案、撰写建议、总结报告 | 自动生成审批说明、客户回复、风险报告等原本需要人工撰写的内容 |
| **容错和自适应** | 失败后只能固定重试或转人工 | 模型可以根据错误信息调整策略（换查询词、降级方案、重新规划） | 减少人工介入频率；提高端到端自动完成率 |
| **覆盖长尾场景** | 低频场景因 ROI 不足不值得建流程 | 同一套图 + 通用模型能力可以覆盖大量长尾变体 | 一个 Agent Graph 替代数十条低频 Workflow |

**收益的代价：**

上述收益并非免费。引入模型意味着：
- 不确定性增加 → 需要 Schema 校验、退出条件、人工审批来约束；
- 延迟和成本增加 → 需要评估哪些节点真正需要模型；
- 可测试性变难 → 需要评测集和 Trace 来保证质量。

**决策原则：**只在传统 Workflow 确实"做不了"或"维护成本过高"的环节引入模型。如果规则可以解决，就不要用模型；如果固定流程可以覆盖，就不要用动态路由。Agent Graph 的目标不是取代 Workflow，而是**在 Workflow 力不从心的地方补上模型的理解和生成能力**。

### 3.4 Goal 与 Planning：Graph 的上游任务契约

Agent Graph 不应该直接执行未经规范化的自然语言。上游 Goal Intake 负责把用户意图转换为包含目标、范围、约束、交付物和成功标准的 Goal；Planner 再根据 Goal 与当前 State 生成由可验证 Subgoal 组成的 Plan。

```text
User Intent → Goal Intake → Goal → Planner → Plan / Subgoals → Graph → Loop → Action
```

| 概念 | 核心问题 | 稳定性 |
| --- | --- | --- |
| Goal | 最终要实现什么，边界和成功标准是什么？ | 相对稳定 |
| Plan | 准备通过哪些子目标和依赖关系实现？ | 可以版本化重建 |
| Subgoal | 当前阶段要产出什么可验证结果？ | 可完成、替换或取消 |
| Loop | 怎样根据反馈完成当前 Subgoal？ | 按轮次动态执行 |
| Action | 这一轮具体做什么？ | 单次动作 |

Graph 只接受经过校验的 Goal 和 Plan。Planner 可以改变路线，但不能静默扩大范围、提升权限或修改成功标准。详细设计见[《Agent Goal 与 Planning：从用户意图到可执行计划》](<../基础机制/03-如何定义目标与计划.md>)。

## 四、Loop、Graph 与 Harness：三层关系

> 核心认识：Agent Graph 不是"整个 Agent"，而是 Agent 应用中的控制流与状态编排层。

### 4.1 完整分层

```text
用户 / 业务事件
        ↓
产品与 API 层：UI、身份、租户、限流、会话
        ↓
Agent Harness：运行循环、权限、沙箱、预算、审批、追踪、恢复
        ↓
Agent Graph：阶段、节点、路由、并行、循环、暂停与状态迁移
        ↓
节点内部：Prompt + 模型参数 + Context Builder + Model / 普通代码
        ↓
工具与知识层：API、MCP、RAG、Memory、代码执行、人工操作
        ↓
传统业务系统：数据库、事务、消息队列、工作流、IAM、审计
        ↓
横切能力：评测、可观测性、安全、成本、部署、版本与回滚
```

### 4.2 Loop 是微观行动，Graph 是宏观结构

Loop 发生在一个节点内部：模型看到 Context，决定是否调用工具，读取结果后再判断，直到产出最终输出。Graph 管理节点之间的阶段关系。

```text
Graph：接单 → 诊断 → 方案 → 审批 → 执行 → 验证
                  │
                  └─ 诊断节点内部可以运行 Tool Loop：
                     观察 → 搜索日志 → 读取结果 → 再搜索 → 得出诊断
```

**组合原则：**让 Loop 处理边界明确的局部探索，让 Graph 控制跨阶段流程、高风险动作、暂停恢复和确定性退出。

当节点由独立的 Agent Worker 执行时，一个用户对话框可以关联多个 Worker Session。Worker 的局部人工问答由原 Session 继续处理；对话控制器负责回传用户答案，Graph 只监督节点状态和跨节点依赖。具体的 Session 关联、交互路由与恢复协议见[《Agent Graph Engineering》第 6.4 节](<02-如何实现Agent Graph.md#64-统一对话框下的多-session-与-worker-human-in-the-loop>)。

### 4.3 Harness 是模型与真实世界之间的执行外壳

Harness 负责把模型能力变成可靠行动：

- 模型适配、Prompt 模板、结构化输出解析和模型降级；
- 执行 Loop、Graph 调度、会话、State、checkpoint 和恢复；
- 工具注册、Schema 校验、超时、重试、幂等和结果标准化；
- 身份传递、最小权限、沙箱、审批、预算和 kill switch；
- 事件流、Trace、日志、Token/成本统计、离线评测和在线反馈。

**Graph 与 Harness 的边界：**Graph 描述"应该按什么结构执行"；Harness 负责"如何安全、可恢复、可观测地执行"。

### 4.4 四种控制方式怎么选

| 任务形态 | 推荐控制方式 | 原因 |
| --- | --- | --- |
| 总结、分类、结构化抽取 | 单次模型调用 | 没有持续行动和业务状态 |
| 开放搜索、短期代码分析 | 受限 Tool Loop | 模型需要动态选择下一步，但边界和时长有限 |
| 固定审批、ETL、订单流转 | 确定性 Workflow | 规则明确，可靠性高于自主推理 |
| 非结构化判断 + 多阶段业务执行 | **Workflow / Graph + 局部 Loop** | 模糊判断与可靠控制同时存在 |

### 4.5 各工程层各自解决什么

| 技术层 | 主要解决的问题 | 它不负责什么 | 典型缺点 |
| --- | --- | --- | --- |
| Model 模型 | 语言理解、推理、生成、模糊判断 | 不天然拥有业务状态、权限和真实执行能力 | 不确定、会产生事实错误、成本和延迟受模型影响 |
| Prompt / Parameters | 规定角色、目标、输出契约 | 不能可靠管理长任务状态、事务和故障恢复 | 对措辞和模型版本敏感，可能出现 Prompt 漂移和参数耦合 |
| Context Engineering | 为当前模型调用构造最小、相关、可信的工作集 | 不决定完整业务流程，也不等于持久化 Memory | 容易上下文膨胀、信息冲突、Prompt Injection 和来源丢失 |
| Agent Loop | 观察 → 判断 → 行动 → 读取结果 → 再判断 | 不天然保证跨阶段顺序、可恢复性和高风险审批 | 可能无限循环、重复调用工具、过程和成本难预测 |
| Agent Graph | 显式表达阶段、路由、循环、并行、状态和恢复点 | 不自动提供安全工具、优质 Context、可靠事务和业务规则 | 图可能膨胀，状态迁移复杂，并增加框架与运行时负担 |
| Agent Harness | 把模型输出变成受控执行 | 不能替代业务建模，也不能凭空提高模型能力 | 建设成本高，容易形成平台锁定，需要长期维护和性能优化 |
| Tools / MCP | 让 Agent 查询数据、调用 API、执行代码 | MCP 只解决连接协议，不决定何时调用和如何继续 | 工具描述错误、权限过大、参数不稳定会把模型错误放大为真实副作用 |
| RAG / Memory | 按需提供外部知识，保存跨会话信息 | 不负责控制流，也不保证检索内容正确或最新 | 召回噪声、过期知识、错误记忆和隐私风险 |
| 传统后端 | 身份、权限、事务、数据库、队列、幂等和业务事实 | 不负责语义理解和开放式推理 | 业务集成复杂，但它仍是可靠性的最终基础 |
| Evals / Observability | 证明是否成功并定位故障 | 不能仅靠日志自动修复错误设计 | 真实评测集昂贵；有 Trace 不等于有正确的 Ground Truth |

# 第二部分：一个案例走完全程

> 学习目标：读完这一部分，你应该能够解释为什么这个任务需要 Graph，画出节点与边，定义最小 State，区分模型和程序的责任，并判断任务失败后应该从哪里恢复。

## 五、贯穿案例：员工申请系统访问权限

员工通过对话提交请求："我是新加入采购项目的同事，需要访问供应商管理系统，下周一开始使用。"系统需要补齐身份和项目信息，查询权限规则，判断风险，创建审批，执行授权并验证结果。

| 维度 | 内容 |
| --- | --- |
| 目标 | 在满足权限和合规要求的前提下完成系统授权 |
| 非结构化输入 | 员工用自然语言描述需求，信息可能不完整 |
| 涉及系统 | 员工目录、项目系统、权限策略库、审批系统、IAM |
| 主要风险 | 越权、错误授权、重复授权、审批绕过、敏感信息泄露 |
| 成功标准 | 正确的人获得正确范围和期限的权限，并留下完整审计记录 |

### 5.1 最小执行图

```text
接收请求
  ↓
提取意图和字段 ──信息不足──→ 追问员工 ──→ 回到字段检查
  ↓ 信息完整
检索权限规则 + 查询员工/项目信息
  ↓
生成候选权限方案
  ↓
确定性风险校验
  ├─ 低风险且规则允许 → 创建标准审批
  ├─ 高风险 → 安全负责人审批
  └─ 规则不允许 → 拒绝并解释原因
  ↓ 审批通过
调用 IAM 授权 → 验证实际权限 → 通知员工 → 结束
```

**为什么不是一个无限循环的 Agent？**因为审批、授权和验证必须有固定顺序；风险校验不能由模型自由决定；授权失败后应该从执行节点恢复，而不是重新生成整套计划。

### 5.2 节点、边与责任分配

| 节点 | 主要输入 | 主要输出 | 责任主体 |
| --- | --- | --- | --- |
| extract_request | 员工原始请求 | 系统、权限、项目、期限 | 模型抽取 + Schema 校验 |
| check_missing | 结构化请求 | 缺失字段列表 | 确定性代码 |
| retrieve_policy | 系统与角色 | 带来源和版本的权限规则 | RAG / 策略服务 |
| propose_access | 请求、员工信息、规则 | 候选权限方案及理由 | 模型 |
| risk_check | 候选方案与业务事实 | 风险等级、允许或拒绝 | 规则引擎 / 代码 |
| human_approval | 方案、证据、风险 | 批准、拒绝或修改 | 审批人 |
| grant_access | 已批准方案 | IAM 操作结果 | 受限工具 |
| verify_access | IAM 结果 | 实际权限与预期差异 | 确定性查询与比较 |

**核心原则：模型提出方案，程序验证规则，人批准高风险动作，工具执行受限操作。**

### 5.3 最小 State

```json
{
  "run_id": "run_20260811_001",
  "requester_id": "erp_xxx",
  "raw_request": "需要访问供应商管理系统",
  "requested_system": "supplier_portal",
  "requested_role": null,
  "project_id": "P2026-0811",
  "duration": "2026-08-17/2026-12-31",
  "missing_fields": ["requested_role"],
  "policy_refs": [],
  "proposed_access": null,
  "risk_level": null,
  "approval_status": "not_started",
  "grant_status": "not_started",
  "retry_count": 0,
  "errors": []
}
```

State 保存任务事实和执行进度，不保存所有聊天文本，也不应该直接成为模型的完整 Prompt。每个节点只读取自己需要的字段，并以结构化增量更新 State。

### 5.4 用同一个案例区分 Context、State、RAG、Memory 与业务数据库

| 概念 | 在本案例中保存什么 | 是否是真实业务事实 |
| --- | --- | --- |
| Context | 当前节点需要看到的请求摘要、相关规则和必要历史 | 不是存储，只是本次模型调用的工作集 |
| State | 当前阶段、缺失字段、风险等级、审批和授权状态 | 是任务运行事实，但不是最终权限事实 |
| RAG | 按系统和角色检索到的权限政策、FAQ、操作手册 | 是外部知识的检索结果，必须保留来源和版本 |
| Memory | 用户偏好的通知方式等跨会话信息 | 需要可修正和删除，不得自动写入未经核实的权限信息 |
| 业务数据库 | 员工身份、项目归属、审批单、IAM 中的实际权限 | 最终权威事实来源 |

### 5.6 两条执行轨迹

**正常路径：**员工请求 → 缺少角色 → 系统追问 → 信息补齐 → 检索到标准项目角色 → 规则校验通过 → 直属负责人审批 → IAM 授权 → 验证一致 → 通知完成。

**高风险路径：**员工请求管理员权限 → 模型给出候选方案 → 规则识别为高风险 → 不允许直接调用 IAM → 安全负责人审批或降级为只读权限 → 审批结果写入 State 后恢复执行。

## 六、失败是如何发生的：调试与恢复

| 故障 | 表面现象 | 应检查的位置 | 工程控制 |
| --- | --- | --- | --- |
| 路由错误 | 普通请求进入高风险审批，或高风险请求被自动放行 | 路由输入、模型结构化输出、规则版本 | 路由测试集；高风险默认拒绝 |
| 重复授权 | 恢复或重试后再次执行写操作 | checkpoint、工具调用记录、业务返回码 | Run ID + Node ID + Business ID 幂等键 |
| 无法退出循环 | 反复追问或不断重新规划 | 退出条件、缺失字段判定、重试计数 | 最大轮次、超时、费用上限、人工接管 |
| 检索污染 | 过期或无关规则影响方案 | 检索查询、来源、版本、权限过滤 | 元数据过滤、来源引用、时效检查 |
| Prompt Injection | 文档内容试图指挥 Agent 绕过规则 | 外部内容进入 Context 的路径 | 数据与指令分离；工具权限不由检索内容决定 |
| 验证不一致 | 工具返回成功，但实际权限没有生效 | 业务系统最终状态 | 执行后查询并比较预期与实际结果 |

**调试顺序：**先确认最终结果是否正确，再检查执行轨迹；依次定位 State、路由、检索、模型输出、工具参数和业务系统结果。不要只阅读最终回答，也不要只依赖模型自评。

## 七、从案例到工程：各层如何协作

### 7.1 IT 权限案例的工程协作映射

| 工程层 | 在权限申请案例中的职责 |
| --- | --- |
| 产品前端 / API | 接收请求、展示补充问题、审批状态和最终结果 |
| 身份与租户 | 确认申请人、审批人、组织和数据访问范围 |
| Agent Graph | 组织抽取、补充信息、检索、风险、审批、授权和验证阶段 |
| Loop | 在诊断或检索节点内动态选择查询动作 |
| Prompt / Context | 让模型看到最小必要信息，并产出结构化候选方案 |
| Harness | 限制工具、暂停等待审批、保存 checkpoint、记录 Trace 和预算 |
| 策略服务 | 用确定性规则判断角色、期限、互斥权限和风险等级 |
| 消息队列 / Worker | 执行长任务、重试和异步通知 |
| IAM 与数据库 | 保存审批与权限的最终业务事实，执行幂等授权 |
| 评测与观测 | 衡量完成率、越权率、人工接管率、延迟、成本和失败节点 |

### 7.2 推荐的工程设计顺序

面对一个新场景，按以下顺序思考设计（注意：这是设计思考顺序，不是项目交付顺序）：

1. **先定义业务结果：**最终要改变什么业务事实，如何客观验证成功。
2. **先画普通 Workflow：**确定哪些步骤完全可以用规则和代码实现。
3. **标出模糊判断点：**只在理解、归纳、动态检索和方案生成处引入模型。
4. **选择控制方式：**单次调用、局部 Loop、确定性 Workflow 或混合 Graph。
5. **定义 State 和 Context：**区分任务事实、模型工作集、外部知识和最终业务事实。
6. **建立 Harness 边界：**工具权限、沙箱、审批、预算、退出、checkpoint、取消和恢复。
7. **设计工具契约：**Schema、校验、超时、重试、幂等、补偿和审计。
8. **先评测再增加自主性：**先证明单节点和低风险链路可靠，再扩大 Loop、并行或多 Agent。

# 第三部分：设计原则与边界

## 八、核心技术设计

### 8.1 State、Context、RAG 与 Memory

| 概念 | 保存什么 | 生命周期 |
| --- | --- | --- |
| State | 任务当前事实、阶段和中间结果 | 一次任务，可持久化恢复 |
| Context | 本次模型调用真正需要看到的信息 | 一次模型调用 |
| RAG | 按当前问题检索的外部知识 | 按需检索 |
| Memory | 跨会话偏好、事实或经验 | 长期，但必须支持修正和删除 |

不要把完整 State、全部历史和所有工具输出直接塞进模型上下文。每个节点只应获得完成当前职责所需的最小上下文。

### 8.2 Prompt、参数与 Context 如何和 Graph 配合

Prompt 定义当前节点的职责、允许使用的信息、输出 Schema 和停止条件；模型参数影响生成的随机性、工具选择和资源消耗。它们不能替代 Graph 的状态与控制流。

| 问题 | 主要由谁负责 |
| --- | --- |
| 模型这一轮应该完成什么任务？ | Prompt / Instructions |
| 模型能看到哪些信息？ | Context Builder |
| 输出必须符合什么结构？ | Prompt + Structured Output Schema + 程序校验 |
| 完成后进入哪个阶段？ | Graph Edge / Router |
| 工具是否允许执行？ | Harness 权限策略与业务规则 |
| 执行失败后从哪里继续？ | Graph State + checkpoint + Harness Runtime |

**常见错误：**用超长 Prompt 描述整套业务流程，再期待模型自行记住阶段和规则。更可靠的方式是——Graph 决定当前阶段，Context Builder 只装配该节点需要的信息，Prompt 只描述本节点职责，程序对输出和副作用做校验。

### 8.3 Context 是每个节点临时构造的工作集

```text
Graph State
   ↓ 选择当前节点需要的字段
固定指令 + 当前请求 + 相关业务事实 + RAG 结果 + 必要工具结果
   ↓ 来源、时效、权限和 Token 预算过滤
Node Context
   ↓
Model Call
   ↓ 结构化输出校验
State 增量更新
```

Graph 解决不了坏 Context：如果输入信息过期、来源不明或混入恶意指令，Graph 只会更稳定地执行错误。

### 8.4 常见图模式

| 模式 | 结构 | 典型场景 |
| --- | --- | --- |
| Pipeline | A → B → C | 文档处理、内容生成 |
| Router | 分类后进入不同分支 | 客服、意图路由 |
| ReAct Loop | Agent ↔ Tool | 开放搜索、动态分析 |
| Planner–Executor | 规划 → 执行 → 校验 | 研究、编程、复杂任务 |
| Reflection | 生成 → 检查 → 修改 | 报告、代码、内容审核 |
| Map–Reduce | 并行处理 → 汇总 | 多文档、批量分析 |
| Human-in-the-loop | 高风险节点暂停审批 | 财务、订单、权限操作 |
| Supervisor–Worker | 主管调度专业节点 | 确需隔离或并行的复杂任务 |

### 8.5 运行语义

- **Checkpoint：**节点完成后保存状态，支持故障恢复和人工审批后继续。
- **幂等：**写操作使用 Run ID、Node ID 和 Business ID 组成幂等键，避免重复扣款、发信或建单。
- **退出条件：**设置最大模型轮次、工具次数、时长、Token、费用和连续失败阈值。
- **并行合并：**明确并行分支如何合并状态以及冲突如何处理。
- **业务事实分离：**Graph State 保存任务进度，业务数据库保存最终交易事实。

## 九、模型与程序的责任边界

| 适合模型 | 必须由程序/规则负责 |
| --- | --- |
| 理解自然语言和非结构化文档 | 身份认证和权限判断 |
| 归纳信息、提出候选方案 | 金额、库存、时间等精确计算 |
| 在白名单工具中做低风险选择 | 事务提交、幂等和一致性 |
| 生成解释和人工可读建议 | 高风险动作审批和审计 |

## 十、使用边界：什么时候用，什么时候不用

### 10.1 六维评分判断法

为以下六项各打 0–2 分：非结构化理解、动态分支、跨系统动作、长任务恢复、审批审计、专业分工。

- **0–4 分：**优先单次 LLM、RAG 或传统工作流；
- **5–7 分：**采用混合工作流，只在少数节点使用 Agent；
- **8–12 分：**值得评估 Agent Graph。

评分之外，还必须满足：数据可获得、工具可接入、结果可验证、人工基线可量化。

### 10.2 不需要 Agent Graph 的场景

- 简单 FAQ：RAG 通常足够；
- 一次总结、翻译、分类或抽取：直接调用模型；
- 固定表单审批：BPM、规则引擎或 RPA 更合适；
- 高频、低延迟、规则明确的交易：确定性服务优先；
- 结果无法验证且错误代价很高：不应直接自动化。

### 10.3 不应完全自动化的领域

- 付款、转账和超过阈值的退款；
- 删除数据、修改权限和发布生产；
- 医疗最终诊断、法律最终意见、招聘淘汰等高影响决定；
- 自动交易和实时安全控制；
- 涉及个人敏感信息但缺少合法授权的操作。

### 10.4 适合优先落地的场景

1. **客服与工单：**意图识别、订单查询、政策判断、风险分级和人工升级。
2. **员工服务：**IT、HR、权限申请、知识查询和流程办理。
3. **合同与文档审查：**解析、条款抽取、制度检索、风险核验和法务复核。
4. **研究与报告：**问题拆解、并行搜索、来源验证、数据分析和事实检查。
5. **数据分析：**元数据查询、SQL 生成、安全检查、执行与结果验证。
6. **研发与运维：**代码分析、修改、测试、告警诊断、Runbook 与受控执行。
7. **销售与运营：**线索研究、客户信息汇总、内容生成和 CRM 更新。

### 10.5 三个典型场景的执行图

**客服退款：**

```text
识别诉求 → 补齐订单号 → 查询订单 → 确定性退款规则 → 风险评分 → 自动处理/人工审批 → 通知 → 审计
```

**合同审查：**

```text
文档解析 → 合同类型路由 → 条款抽取 → 制度检索 → 风险分析 → 引用核验 → 法务复核 → 红线建议
```

**生产告警：**

```text
告警去重 → 关联变更 → 查询日志/指标 → 根因假设 → 只读诊断 → 推荐 Runbook → 人工批准 → 执行 → 验证/回滚
```

## 十一、Agent Graph 自身的缺点与使用代价

| 缺点 | 为什么发生 | 缓解方式 |
| --- | --- | --- |
| Graph 膨胀 | 把每个 Prompt、工具和异常都建成节点 | 按稳定业务阶段划分节点；局部探索留在受限 Loop |
| State 强耦合 | 所有节点共享大型 State | 小型 Schema、节点最小读写集、状态版本和迁移测试 |
| 延迟与成本增加 | 多次模型调用、持久化、评测和审批叠加 | 减少不必要节点；小模型路由；缓存；并行；预算上限 |
| 错误被流程放大 | 早期错误进入 State，影响后续所有节点 | 关键节点证据校验、置信度门、人工审批和独立验证 |
| 副作用与恢复复杂 | checkpoint 能恢复状态，但外部写操作可能已执行 | 幂等键、执行记录、补偿事务和执行后验证 |
| 框架锁定 | 状态和部署接口依赖具体运行时 | 业务 State 与框架对象分离；工具使用标准契约 |
| 调试困难 | 模型、Prompt、Context、Graph、Harness 都可能是根因 | 分层 Trace、固定评测集、回放和版本记录 |
| 虚假的确定性 | 图看起来可控，但节点内的模型仍然不确定 | 对最终事实和副作用做程序化验证 |

# 第四部分：落地路线

## 十二、从 0 到 1 的实施路径

### 12.1 选择第一个项目

第一个项目应满足：频率高、人工步骤清楚、有脱敏历史样本、结果可验证、动作低风险或可逆，并且有明确业务负责人。**不要从跨十几个系统的"企业万能助理"开始。**

### 12.2 定义最小状态图

```text
START → understand → retrieve → draft → validate

validate 成功        → respond
validate 可修正失败  → draft（限制重试次数）
validate 高风险      → human_approve
工具或系统不可用     → fallback / handoff
```

### 12.3 实施顺序

1. 定义输入、输出和端到端成功标准；
2. 区分确定性步骤与需要模型判断的步骤；
3. 设计 State Schema、节点职责和所有失败路径；
4. 先接只读工具，再开放低风险、可逆写操作；
5. 加入 checkpoint、幂等、超时、预算和人工审批；
6. 准备真实脱敏任务集，在影子模式与人工结果对比；
7. 小流量开放受限自动化，持续评测和灰度升级；
8. 只有出现权限、上下文、专业知识或并行隔离需求时再增加多 Agent。

### 12.4 从现有 Workflow 引入 Agent Graph

> 大多数企业不是从零开始，而是已有 Workflow 系统在运行。正确的引入方式不是替换，而是在 Workflow 力不从心的点上嵌入模型能力。

#### 引入原则

1. **不替换，而是扩展：**现有 Workflow 的调度、状态、checkpoint 和监控全部保留，模型只作为一种新的节点类型嵌入。
2. **按风险分层引入：**容错高的场景先做，容错低的场景先跑影子模式积累数据。
3. **每次只改一个节点：**不要一次重构整个流程，而是在单个痛点处插入模型节点，验证有效后再扩展。
4. **始终保留降级路径：**模型节点失败或置信度低时，自动回退到原有路径或转人工。

#### 第一步：给现有引擎扩展 LLM 节点类型

无论是自研引擎还是 Activiti/Camunda/n8n，核心改动是增加一种可配置的 LLM 节点：

```text
LLMNode 的最小约束：
├── 输入 Schema：从 Workflow State 中取哪些字段传给模型
├── 输出 Schema：模型必须返回结构化结果，经程序校验后写回 State
├── 超时与重试：模型调用失败有明确的兜底策略
├── 降级方案：模型不可用或置信度低 → 走原有路径或转人工
├── 监控与审计：纳入现有 Workflow 的日志、Trace 和告警体系
└── 成本控制：Token 预算、调用次数上限
```

这一步的目标是让模型成为 Workflow 中一种"可插拔的执行器"，而不是重建整个流程系统。

#### 第二步：按风险和痛感选择切入点

| | 容错高（内部、可逆、有人兜底） | 容错低（面客、资金、不可逆） |
| --- | --- | --- |
| **痛感强**（量大、积压多、人工耗时） | **第一优先级：** 立刻做，快速见效 | **第三优先级：** 先跑影子模式 |
| **痛感弱**（低频、尚可维持） | **第二优先级：** 有余力时扩展 | **暂不引入** |

#### 第三步：三种典型引入模式

**模式 A：前置理解层——解决"入口需要人工整理"**

```text
之前：人工分拣邮件/聊天 → 手动填字段 → 启动 Workflow
之后：LLMNode（抽取意图和字段） → 校验节点 → 启动原有 Workflow
      │
      └── 置信度低或校验失败 → 仍转人工分拣
```

- 现有 Workflow 完全不改，只在入口前加一层；
- 模型输出经过 Schema 校验，不合格则降级；
- 适用：工单分类、邮件意图识别、文档字段抽取、聊天请求结构化。

**模式 B：生成辅助层——解决"某些节点需要人写东西"**

```text
之前：... → 人工撰写（回复/摘要/报告/审批意见） → 下一步
之后：... → LLMNode（生成草稿） → 人工确认或微调 → 下一步
```

- 人工从"从零撰写"变成"审一眼确认"，效率通常提升 3-5 倍；
- 保留人工确认环节，风险可控；
- 适用：客服回复草稿、审批意见生成、风险说明、会议纪要、合同摘要。

**模式 C：异常智能分流——解决"兜底全转人工导致积压"**

```text
之前：规则匹配 → 匹配成功 → 自动处理
               → 匹配失败 → 全部转人工队列（大量积压）

之后：规则匹配 → 匹配成功 → 自动处理
               → 匹配失败 → LLMNode（分析原因 + 分类 + 建议方案）
                             → 人工确认执行
                             → 模型也不确定 → 转高优人工队列
```

- 消化的是"规则覆盖不了"的长尾流量；
- 人工从"从头分析"变成"看建议做决定"；
- 适用：异常工单、规则外退款、非标审批、无法自动分类的请求。

#### 第四步：容错低场景的影子模式

对不能容错的场景（面客、涉及资金、不可逆操作），不直接切入，而是用影子模式积累数据：

```text
生产路径（不变）：原有规则/人工 → 正常执行 → 记录人工结果
影子路径（旁路）：同时调 LLMNode → 记录模型结果 → 不执行任何动作
                                                   ↓
                                            自动对比模型 vs 人工
                                            积累评测数据集
                                            准确率达标 → 灰度切入
```

影子模式的价值：
- 零风险：模型结果只记录不执行；
- 自动生成评测集：人工结果就是 Ground Truth；
- 数据驱动决策：用准确率和一致率决定是否切入，而不是凭感觉。

#### 第五步：分阶段推进路线

| 阶段 | 目标 | 做什么 | 验证标准 |
| --- | --- | --- | --- |
| 0 - 基础能力 | 引擎支持 LLM 节点 | 扩展节点类型、降级、监控、成本控制 | 能在任意 Workflow 中插入模型节点 |
| 1 - 快速验证 | 证明价值 | 选 1-2 个容错高+痛感强的流程，用模式 A 或 B 改造 | 人工工作量下降，无严重错误 |
| 2 - 消化积压 | 扩大覆盖 | 对异常分支用模式 C | 人工积压减少，处理时长下降 |
| 3 - 积累数据 | 准备高风险切入 | 容错低场景开影子模式 | 模型 vs 人工一致率持续统计 |
| 4 - 灰度替换 | 逐步切入高风险 | 影子数据达标的场景，小流量切入 | 业务指标不回退 |
| 5 - 深度改造 | 重构为 Agent Graph | 多个 LLM 节点 + 动态路由 + 循环形成完整 Graph | 端到端自动完成率达标 |

#### 引入时的常见错误

| 错误做法 | 为什么有问题 | 正确做法 |
| --- | --- | --- |
| 一次性用 Agent Graph 重写整个 Workflow | 风险高、周期长、无法验证 | 在单个节点嵌入模型，逐步扩展 |
| 模型直接做最终决策 | 不确定性无法保证 | 模型给建议，程序或人做决策 |
| 没有降级路径 | 模型不可用时流程中断 | 每个 LLM 节点都有超时降级方案 |
| 只看 Demo 效果就上线 | Demo 输入和生产输入差异大 | 必须用生产脱敏数据做评测 |
| 所有场景同时引入 | 无法定位问题、无法衡量收益 | 一次一个场景，验证后再扩展 |
| 用影子模式但不建对比机制 | 数据白跑了 | 建立自动对比和准确率统计 |

## 十三、评测与运营

Graph 的验证重点是路由：缺信息是否返回追问、审批拒绝是否结束、失败是否进入正确恢复路径、并行分支是否正确合并。最终任务结果仍须用业务事实判定。

评测样本与评分方法见[如何评测 Agent](<../质量与实践/01-如何评测Agent.md>)；节点、路由和工具的分层工程测试见[Graph Engineering](<02-如何实现Agent Graph.md#十四测试与评测工程>)。记录每条运行的路径、状态变化和失败原因，才能把结果退化定位到具体分支。

## 十四、安全与治理

Graph 控制“什么时候允许进入下一阶段”；工具执行器仍须独立检查身份、资源和参数权限。不要因为一条边来自审批节点，就默认后续任何动作都已获批。

威胁模型、审批绑定和副作用控制见[权限与提示注入防护](<../运行与连接/04-Agent权限与提示注入防护.md>)；这里重点验证拒绝、取消、失败与恢复路径不会绕过授权边界。

## 十五、上线前检查清单

### 场景

- [ ] 目标、人工基线和成功标准清晰；
- [ ] Goal Intake 能利用页面、会话、策略和工具补全信息，而不是要求用户填写完整规格；
- [ ] 自动补全字段保留来源、置信度和关键假设；
- [ ] 只在高影响且无法安全推断的信息上询问用户；
- [ ] 结果可以客观验证；
- [ ] 第一阶段动作低风险或可逆；
- [ ] 有业务负责人处理异常。

### 技术

- [ ] State、Context、RAG 和 Memory 分离；
- [ ] 子目标描述可验证结果，而不是预设工具调用序列；
- [ ] 主 Goal 和安全约束稳定，子目标支持滚动规划；
- [ ] Goal 与 Plan 分开存储和版本化，每次 Replan 都记录原因和替代关系；
- [ ] Replan Gate 能阻止范围扩大、权限提升和成功标准被静默修改；
- [ ] 节点责任、边和失败路径清晰；
- [ ] checkpoint、恢复、重试、取消和幂等已测试；
- [ ] 最大步数、预算和退出条件已设置。

### 安全

- [ ] 身份、租户和工具权限贯穿全链路；
- [ ] 高风险动作必须审批；
- [ ] Prompt Injection、越权和数据外泄用例已测试；
- [ ] 有审计、回滚和 kill switch。

### 评测与运营

- [ ] 有正常、失败、边界和恶意输入测试集；
- [ ] 同时评估最终结果与执行轨迹；
- [ ] 上线经过影子模式和小流量；
- [ ] 模型、Prompt、工具和 Graph 均可版本化与回滚。

框架、平台、托管运行和产品生态属于时间敏感内容，已集中到[《Agent 框架、平台与产品生态参考》](<../references/Agent 框架、平台与产品生态参考.md>)。本文只保留稳定的 Graph 概念、场景、边界和落地原则；具体选型前请核对参考页与官方资料。

## 常见误区速查

| 误区 | 正确理解 |
| --- | --- |
| Agent Graph = 多 Agent | 多数第一版只需要单 Agent、明确节点和确定性工具 |
| 用户必须填写完整 Goal | 用户表达自然意图；系统负责规范化、补全和拆分，只追问高影响歧义 |
| Goal Decomposer 应直接生成工具序列 | 应生成带完成标准的子目标，再由节点内 Loop 动态选择工具 |
| Plan 是 Goal 的一部分 | Plan 由 Goal 和 State 派生；Goal 相对稳定，Plan 可以版本化重建 |
| Plan 执行完就代表任务完成 | 是否完成由 Goal 的成功标准决定，而不是步骤是否全部走完 |
| Graph 一定是 DAG | 追问、重试、反思天然形成循环 |
| 使用框架 = 具备生产能力 | checkpoint、幂等、权限、评测和回滚仍需业务系统实现 |
| Memory = 聊天历史 | 长期信息必须经过核实，并支持修改、删除和来源追踪 |
| MCP 负责编排 | MCP 解决工具连接；Graph 决定何时调用、调用后如何继续 |
| 模型推理 = 可靠控制 | 模型处理模糊判断，但金额、权限、库存必须由程序守住 |

## 理解检查

以下问题用于验证是否真正理解，而非记住了框架名称：

1. 为什么用户不需要手工填写完整 Goal？系统还能从哪些来源补全信息？
2. Goal Normalization 和 Goal Decomposition 有什么区别？
3. 哪些缺失信息可以默认或查询，哪些必须询问用户？
4. 为什么子目标应该描述结果，而不是预设工具调用序列？
5. 为什么 Plan 不应该作为 Goal 的一个可随意修改字段？
6. 什么变化属于 Replan，什么变化已经构成 Goal 变更？
7. 为什么 Plan 中的步骤全部完成，任务仍可能没有成功？
8. 如果把"员工申请权限"改成"客服退款"，哪些 State 字段、工具和风险边界必须变化？
9. 哪些节点可以直接使用普通代码，完全不需要 LLM？为什么？
10. 如果审批完成后服务重启，Graph 应该从哪里恢复？如何避免重复授权？
11. 为什么检索到的权限政策不能直接修改工具权限？
12. 什么时候值得把一个节点拆成独立 Agent？拆分后增加了哪些成本和风险？

**最小验证集：**

- **正常案例：**信息完整、规则允许、审批通过、授权成功。
- **失败案例：**IAM 超时后恢复，确保不会重复授权。
- **权限边界案例：**请求管理员权限或输入包含 Prompt Injection，确认系统不会绕过审批。

> **完成判断：**如果你能独立画出案例的图，说明每个节点读取和更新哪些 State，指出模型、程序、人和工具各自负责什么，并设计上述三类测试，就已经掌握了 Agent Graph 的核心。

## 结语

Agent Graph 的意义不是让模型拥有无限自主权，而是给模型的判断能力建立一个可以运行在真实业务系统中的控制结构。模型负责理解模糊世界，代码负责守住确定性；图负责连接两者，状态负责让任务能够继续，权限和审批负责限制风险，评测与观测负责证明任务真的完成。

第一个 Agent Graph 项目的正确目标，不是做一个无所不能的 Agent，而是把一个高频、可测量、边界清晰的业务闭环，从人工辅助逐步推进到受控自动化。

> **最终判断：**Agent Graph 的作用不是取代 Prompt、Context、Loop、Harness 或传统软件工程，而是把它们连接成可理解的任务结构。真正的生产可靠性来自分层责任：模型处理模糊世界，Graph 管理任务结构，Harness 约束执行，传统系统守住业务事实，评测与观测证明结果。
