# Multi-Agent Patterns：何时拆分与如何协作

> [Agent Graph](<01-什么时候需要Agent Graph.md>)管理宏观控制流；[A2A](<../运行与连接/03-如何用A2A连接Agent.md>)处理独立 Agent 间通信。本文负责“为什么拆、拆成什么、如何验证协作”。多 Agent 是一种组织选择，不是 Agent 成熟度等级。

## 一、先证明拆分有收益

优先尝试单 Agent 加明确的工具、状态与工作流。只有下列变化方向清楚时再拆：不同权限或数据域必须隔离；专业能力和 Context 明显不同；可独立并行且汇总规则明确；远端团队独立维护服务。若只是 Prompt 很长或任务看起来复杂，先检查 Context 和节点粒度。

## 二、常见模式

| 模式 | 控制方式 | 适用条件 | 主要代价 |
| --- | --- | --- | --- |
| Router → Specialist | 路由器选择一个专业执行者 | 输入类别清楚、专业能力不同 | 错路由与回退 |
| Supervisor → Workers | 主控拆分、派发、验收 | 可独立交付局部结果 | 协调与上下文复制 |
| Parallel specialists | 多方并行生成独立证据 | 子任务相互独立、可合并 | 成本、冲突与尾延迟 |
| Handoff | 转交控制权给另一执行者 | 权限或职责有明确移交点 | 会话连续性和责任归属 |

不要让 Worker 任意互相调用。协调层应有明确的任务 ID、所有权、预算和升级路径；Worker 回传结构化结果、证据引用、未解决问题和状态，不直接改写其他 Worker 的 State。

## 三、协作契约

一次委托至少写清：局部目标、输入材料及其权限、允许工具、输出 Schema、完成标准、超时/取消、失败如何回传。主控验收时核对结果来源和业务事实，再合并进全局 State；自然语言结论不能自动升级为事实。并行结果冲突时，保留双方证据，按权威来源复核或交给人处理。

远端 Agent 需要任务生命周期和身份传递时可使用 A2A；同一进程内的子任务不必为协议而协议化。通信方式不替代授权、幂等与业务验收。

## 四、怎样评测是否值得拆

用同一批任务比较单 Agent 基线与多 Agent 方案：成功率、越权率、证据质量、端到端延迟、Token/费用、人工接管率及失败恢复。若新增角色没有改善这些目标中的明确一项，保留更简单的结构。对并行场景，特别测试一个 Worker 超时、两个 Worker 结论冲突、重复回传和用户中途取消。

## 五、完整例子：订单诊断是否要拆成两个 Worker

先做单 Agent 基线：按需查询指标和日志，在同一 State 中保留证据并形成结论。若工具数量少、权限相同、任务不长，这样通常更容易调试。

当日志量很大且指标分析与日志分析可独立推进时，可以试验两个 Worker：

| 角色 | 输入与工具范围 | 输出 |
| --- | --- | --- |
| 指标 Worker | 同一服务、环境、时间窗；只读指标工具 | 指标异常、来源、时间、未验证假设 |
| 日志 Worker | 同一任务范围；只读日志工具 | 错误模式、来源、时间、缺失信息 |
| 主控 | 两份结构化结果与原始 Goal | 核对范围、处理冲突、形成结论 |

主控先传统一时间窗，防止两个 Worker 分析不同事故。Worker 无法取得数据时返回 `needs_information` 或 `failed`，由主控决定补充、重试或收尾。两个 Worker 都读到同一份报告，不应被当作两类独立证据。

如果指标 Worker 超时，主控可以报告已有观察和缺口；如果两份结果冲突，应核对时间、来源与适用范围。不要简单投票决定事实。用同一评测集比较拆分前后的结果、成本和延迟；并行节省的时间可能被协调和重试消耗。

**常见错误：**只按角色名称拆 Agent；各自保存互相冲突的任务事实；主控无条件接受 Worker 结论；取消任务后未停止 Worker 的后续调用。

**自检：**删掉一个 Worker 后系统失去了什么明确能力？如果只减少了一轮转述，就应重新评估拆分价值。
