# State、RAG 与 Memory：信息放在哪里

> [Agent Loop](<01-Agent如何运行：Loop.md>)说明 State 如何支持当前执行；本文负责区分会话、任务状态、检索知识和跨任务记忆，并说明它们的读写边界。

## 一、先按生命周期和权威来源分类

| 信息 | 放在哪里 | 例子 | 谁可以更新 |
| --- | --- | --- | --- |
| 当前对话原文 | 会话记录 | 用户原话、澄清回答 | 对话系统追加 |
| 本次任务事实与控制状态 | State / checkpoint | 当前假设、工具结果引用、审批状态 | 应用按规则更新 |
| 外部资料 | 文档库 / 业务系统，通过 RAG 按需读取 | 故障手册、政策、工单 | 原始系统维护 |
| 跨任务可用的信息 | Durable Memory | 用户明确保存的偏好、已核实的长期背景 | 经授权和写入策略维护 |
| 大型过程产物 | Artifact 存储 | 完整日志、报告、代码文件 | 产物系统保存，State 留引用 |

**判据：**“本次任务结束就失效”通常进 State；“可从权威系统重取”留在原系统并按需检索；“未来任务确实需要且允许保留”才考虑 Memory。不要把完整对话当作自动增长的长期记忆。

## 二、State：可信程度比字段数量重要

State 至少区分 `observations`（带来源和时间的观察）、`hypotheses`（可被推翻的推断）、`actions`（执行记录）和 `control`（步骤、预算、审批、状态）。工具返回成功只证明调用过程成功，不自动证明业务结果正确。外部结论经过 Schema 校验后仍可能是假设；只有独立证据或业务系统核验后才升级为事实。

Checkpoint 用于恢复任务，不等于跨任务 Memory。恢复后仍要核对可能已经变化的外部状态；带副作用的动作还需要幂等键与实际状态核查。参见[Graph Engineering 的恢复章节](<../编排与协作/02-如何实现Agent Graph.md>)。

## 三、RAG：从问题到可核对证据

一个最小检索链路是：确定问题和身份 → 权限过滤 → 召回候选资料 → 选择相关片段 → 连同来源、时间或版本交给模型 → 在答案中引用或核对。可先用关键词检索；只有语义召回确实改善样本任务时，才增加向量索引或混合检索。

要分别检查三类失败：

1. **没找到：**资料确实不存在、索引延迟、查询词不匹配，还是权限过滤正确地排除了它？
2. **找错了：**片段相关但属于旧版本、其他租户或类似却不同的业务规则。
3. **用错了：**检索正确，模型却忽略来源、把示例当事实或照做文档中的恶意指令。

评测检索时同时记录召回结果和最终任务表现。命中一段“看起来相关”的文字，不代表回答正确。

## 四、Memory：读、写、改、删都要有策略

一次 Memory 写入建议包含：内容、类别、来源、取得方式、写入时间、有效期或复核条件、适用范围、用户可见性。模型提出“记住这个”只能是候选；应用检查用户授权、必要性、敏感性、可信度与重复/冲突后再写入。

读取时只取当前任务相关且当前身份有权看的记忆，向模型标明它是历史信息而非现时事实。用户更正或要求删除时，要能定位原记录及其索引/缓存；若无法可靠同步删除，就不要承诺已经完全遗忘。

**例子：**“用户偏好简短中文回答”可作为经确认的偏好记忆；“订单接口今天延迟升高”是带时间的任务观察；“公司故障手册规定先查连接池”属于知识库资料。三者不应写到同一存储并用同一种可信度处理。

## 五、最小实践

用三份小型故障手册做只读诊断：先用关键词检索，返回文档 ID、版本、更新时间和片段；State 保存引用及观察结果；下一次任务仅在用户明确需要时读取长期偏好。再加入一份过期手册和一份其他租户手册，确认系统不会引用它们。评测方法见[Agent Evaluation](<../质量与实践/01-如何评测Agent.md>)。

## 六、完整例子：从检索手册到有引用的诊断

**任务：**用户想知道订单接口为什么慢，只允许读取本团队数据。应用有以下教学资料：

| 文档 | 内容与状态 | 本轮能否使用 |
| --- | --- | --- |
| `orders-guide-v2` | 当前有效手册：连接池满时检查等待、占用时长和释放情况 | 可以，用户有权限 |
| `orders-guide-v1` | 已被 v2 替代，使用旧指标名称 | 不作为当前操作依据 |
| `payments-incident` | 其他团队的故障记录，语义很相似 | 不可以，用户无权限 |

完整流程如下：

1. **准备资料。**按章节或完整语义段切分，片段保留文档 ID、版本、标题、权限和有效状态；拆分后仍能定位原文。增量更新时使旧版本片段失效。
2. **构造查询。**从当前 Goal 和观察提取“orders、连接池满、请求等待”。不要把完整聊天和无关个人信息发给检索服务。
3. **过滤与召回。**在受控数据范围内查找候选片段；检索后的结果交付模型前再次保证权限有效。关键词检索可作为起点，语义检索或重排需要用任务样本证明收益。
4. **检查适用性。**确认找到的是当前环境和有效版本。文档写“应检查连接释放”只是一条诊断建议，并不能证明这次故障就是连接泄漏。
5. **调用只读工具补证据。**按手册检查指标与日志，把当前观察写入 State，文档片段仍保留在知识库或 Artifact 中。
6. **生成带引用的报告。**例如：“当前指标显示连接池已满；日志出现等待超时。按 `orders-guide-v2` 的连接池章节，下一步应核查连接释放与占用时长。现有证据尚未证明连接泄漏。”

如果只有旧版手册可用，应说明适用性无法确认，再请求新资料或限制结论。不能把旧版、其他租户资料或相似事故补成当前事实。

**怎么验证：**分别测试“资料不存在”“正确资料没被召回”“召回了正确资料但答案用错”三种情况。它们需要不同的修复，不能统一归结为模型不够好。

## 七、完整例子：一条偏好记忆的生命周期

用户明确说：“以后技术解释先给结论，再给例子，请记住。”应用可以建立一条范围清楚的偏好记录：

```json
{
  "memory_id": "pref-001",
  "subject": "current_user",
  "kind": "response_preference",
  "value": "技术解释先给结论，再给例子",
  "source": "user-explicit-request:message-17",
  "scope": "technical_explanations",
  "status": "active"
}
```

这是示意结构，不是某个 Memory SDK 的接口。应用还应维护写入时间、适用账户、可见性及保留规则。

| 阶段 | 应用行为 | 不应发生的事 |
| --- | --- | --- |
| 写入 | 确认是用户明确表达且允许保存的偏好 | 从一次模型推测生成用户画像 |
| 读取 | 在相关技术解释中取出，作为可被当前请求覆盖的偏好 | 将旧偏好升级为不可更改的系统规则 |
| 更正 | 用户改为“这次先详细推导”时仅作用于本次；若明确说“以后都这样”，再更新长期记录 | 把一次临时要求误当永久改变 |
| 冲突 | 保留新旧记录的来源和更新关系，采用最新明确指示 | 把相互冲突的偏好一起塞入 Context |
| 删除 | 按 ID 删除或失效化有效记录，处理检索索引和缓存，并说明实际完成范围 | 主库已删而旧索引仍会召回，却声称完全删除 |

这条偏好跨任务使用；本次诊断中“已查询一次日志”“审批尚未完成”仍属于任务 State。记录是否存得很久，不能单独决定它属于哪一类。

## 八、设计取舍与理解检查

先问“以后哪个决策需要这条信息、谁对其真实性负责”，再选择存储与检索方式。小型静态资料不必立即引入向量数据库；经常变化的业务事实更适合按需查权威系统。

**自检：**当用户改正一个事实时，State、Context、Memory 和知识库中哪些副本需要更新？如果你无法指出该事实的权威来源，后续检索和压缩就可能不断放大错误。
