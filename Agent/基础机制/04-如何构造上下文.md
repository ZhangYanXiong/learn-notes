## 一、从一次决策倒推所需信息

先写清模型这一轮要做的决定，再选择信息。订单接口诊断的“选择下一项只读检查”只需要：诊断目标、已验证事实、尚未排除的假设、可用只读工具及其参数、剩余预算。它不需要整段聊天历史，也不需要其他服务的日志。

| 来源 | 用途 | 进入条件 |
| --- | --- | --- |
| 固定指令与输出契约 | 定义角色、动作格式和边界 | 由应用提供并版本化 |
| 当前 Goal 与约束 | 告诉模型要完成什么 | 每轮传入相关部分 |
| State 摘要 | 已验证事实、进度、预算 | 按当前决策投影，不直接倾倒完整 State |
| 近期交互与工具结果 | 解释刚发生的变化 | 保留与下一步有关的内容 |
| 检索材料与长期 Memory | 提供外部知识或偏好 | 相关、授权、带来源和时间 |
| 工具 Schema | 限定本轮可请求的动作 | 只暴露当前身份和阶段允许的工具 |

## 二、一个 Context Builder 的输入输出契约

```text
输入：Goal、当前节点/任务、结构化 State、调用者身份、工具权限、
      检索结果、Token 预算、上一次决策和结果
输出：本轮消息/内容块 + 来源清单 + 被省略信息的原因 + 估算预算
```

构造顺序建议为：

1. 确定当前决策、成功标准和不可跨越的权限边界。
2. 从 State 提取必要字段；事实附来源与观察时间，推断明确标注为假设。
3. 仅检索当前问题需要的资料，并先做身份、租户和文档权限过滤。
4. 对大型工具结果保留原始 Artifact 引用，提取与决策相关的片段；摘要不能替代可核对的证据。
5. 按预算压缩低优先级内容，最后校验必需约束、来源和最新事实没有被压掉。

这一步属于应用控制。模型可以建议还需要什么信息，但不能决定给自己增加权限或把外部文本提升成系统指令。

## 三、压缩、冲突与时效

- **优先保留：**目标、硬约束、当前阶段、已验证关键事实、未完成动作、审批状态和最近失败原因。
- **可以摘要：**较早的交互、重复日志、已结束分支；摘要记录原始引用，必要时重新读取。
- **不要靠摘要解决冲突：**两个来源结论不同，保留双方来源和时间，查询权威系统或向用户说明不确定性。
- **时效必须可见：**“昨天的连接数”不能无提示地支持“现在的故障”。实时指标要写观察时间和有效范围。
- **预算不足时：**先缩小检索范围或分步查询；如果完成决策必需的证据放不下，应暂停或改变任务策略，不能默默丢掉关键约束。

## 四、信任边界

网页、检索文档、日志、仓库文件、工具描述和远端 Agent 产物都可能带有指令样式的文本。将它们放在标记为“外部数据”的内容中，保留来源；工具执行前由程序重新做参数、身份和权限校验。仅写“忽略恶意指令”的 Prompt 不能代替这些边界。详见[安全专题](<../运行与连接/04-Agent权限与提示注入防护.md>)。

## 五、怎样验证 Context 设计

为同一决策准备三类样本：正常材料、无关信息大量混入、包含冲突或注入的材料。检查：

- 模型是否引用了可追溯的事实，而不是过期摘要；
- 必需约束是否在压缩后仍被遵守；
- 不同身份是否只看到各自可见的材料和工具；
- 移除无关内容后，任务结果与成本是否改善；
- 证据缺失时是否选择查询或说明不确定，而不是编造。

**练习：**针对“只做订单接口诊断”分别构造“选下一项检查”和“生成最终报告”的 Context Contract。前者需要工具 Schema 和假设，后者需要已验证证据及其来源；比较两者为什么不应使用同一份完整上下文。

## 六、完整例子：把一段诊断历史变成下一轮 Context

**问题：**订单接口响应变慢，用户只授权诊断。上一轮已经查询指标；这一轮要决定下一项检查。以下数据均为教学假设。

原始材料有：用户的只读要求、20 页监控返回、最近 30 轮聊天、其他服务的排障记录、当前连接池利用率 100% 的观察，以及“可能是连接泄漏”的假设。全部放进模型会混合约束、事实和推断。

| 材料 | 本轮处理 | 原因 |
| --- | --- | --- |
| 只做诊断，禁止修改生产 | 完整保留为应用提供的约束 | 直接限制行动 |
| 当前服务、环境、查询时间 | 完整保留 | 工具参数与证据适用范围 |
| 指标原始返回 | 保存 Artifact，只选关键观察和引用 | 可复查，避免大量无关数据 |
| “连接泄漏”推断 | 标为未验证假设 | 不能当作已证实原因 |
| 其他服务的历史排障 | 本轮省略 | 尚无关联证据 |
| 日志读取工具 | 暴露参数 Schema | 当前阶段已授权且可补充证据 |
| 重启、部署工具 | 不暴露，执行层也拒绝调用 | 超出本次授权 |

得到的工作集可以表达为下面的框架无关数据结构：

```json
{
  "goal": "诊断订单接口延迟，给出有证据的最可能原因",
  "constraints": ["只读", "证据不足时明确说明"],
  "scope": {"service": "orders", "environment": "production"},
  "observations": [{
    "fact": "连接池使用率 100%",
    "source": "metrics:sample-01",
    "observed_at": "2026-10-16T10:00:00+08:00"
  }],
  "hypotheses": [{"claim": "可能有连接泄漏", "status": "unverified"}],
  "available_tools": ["read_logs"],
  "next_decision": "选择一次能支持或排除假设的只读检查"
}
```

模型请求读取同一服务、同一时间范围的日志后，程序验证参数、执行工具，再更新 State。生成最终报告时重新构造 Context：保留证据和不确定性，通常无需再传工具选择历史。原始材料保留在 Artifact 中，不因上下文压缩而被删除。

**预算取舍：**先为输出和必需约束留空间，再分配检索片段与历史。具体 Token 数由所用模型的计量方式和任务评测决定；不能把字符数直接当 Token 数。若关键证据被压缩成“指标异常”，就丢失了数值、范围与时间，应重新读取或重做摘要。

## 七、常见错误与理解检查

- 把假设写入“事实摘要”：后续每轮都会继承未经验证的结论。
- 只靠 Prompt 写“只读”：工具执行器仍需拒绝越权请求。
- 摘要后丢掉来源：无法核实是否压缩失真，也无法判断时效。

**自检：**如果用户中途把目标从诊断改成修复，哪些约束需要重新确认？如果同一指标出现两个时间点的不同值，怎样避免把它们误当成互相矛盾的当前事实？
