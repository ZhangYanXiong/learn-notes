## 一页结论

1. **Agent Loop 是模型参与决策的受控执行循环。**它不断重复“观察 → 决策 → 行动 → 读取结果 → 评估”，直到目标完成、需要人工介入或命中停止条件。
2. **Loop 不等于一个无限 `while`。**生产 Loop 必须有最大步数、超时、预算、权限、审批、失败处理和明确的完成判定。
3. **模型负责模糊判断，程序负责确定性控制。**模型可以决定下一步查什么、调用哪个工具；参数校验、权限检查、真实执行、幂等和停止条件必须由应用程序控制。
4. **Context 不是 State。**Context 是本轮临时交给模型的工作集；State 是应用维护的任务事实。工具结果不应不加选择地永久堆进 Prompt。
5. **Loop 适合边界明确的局部探索。**开放搜索、代码诊断、资料整理和短任务助手很适合；固定审批、跨阶段长任务和高风险业务流程更适合由 Workflow / Agent Graph 控制，并只在局部节点中使用 Loop。
6. **Loop 的质量不取决于“思考了多少步”，而取决于是否用尽可能少且安全的动作完成了可验证目标。**生产评测必须同时关注任务成功、工具正确性、步骤效率、成本、延迟和副作用安全。

# 第一部分：心智模型

> 核心结论：Agent Loop 不是让模型自由运行，而是由应用程序不断向模型提供受控观察、接收下一步动作、执行并反馈结果的闭环。

## 一、为什么需要 Loop：从一次回答到持续行动

一次普通模型调用的结构是：

```text
输入 → 模型 → 输出
```

它适合总结、翻译、分类、抽取和一次性生成。但下面这些任务无法提前知道完成它需要几步：

- 搜索资料时，不知道第一次查询能否找到答案；
- 排查故障时，需要根据日志结果决定下一项检查；
- 修改代码时，需要根据测试失败信息继续定位和修复；
- 处理文件时，需要先查看目录，再决定读取、修改或创建哪些内容；
- 个人助理任务中，需要根据日历、邮件或业务系统的返回结果继续判断。

这些任务的共同点是：**下一步依赖上一步观察到的结果。**因此控制结构从一次调用变成闭环：

```text
              ┌─────────────────────────────┐
              │                             │
              ▼                             │
目标 → 构造观察 → 模型决策 → 执行动作 → 返回结果 → 评估
                                      │          │
                                      │          ├─ 未完成：继续循环
                                      │          ├─ 需审批：暂停
                                      │          └─ 已完成：结束
                                      │
                                      └─ 工具失败：重试 / 换策略 / 降级
```

## 二、Agent Loop 是什么

可以把 Agent Loop 表达为：

```text
Agent Loop = Goal + Observation + Decision + Action + Feedback + State + Stop Rules
```

| 组成 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| Goal 目标 | 最终要完成什么？ | 回答问题、定位故障、修改代码、整理报告 |
| Observation 观察 | 模型这一轮能看到什么？ | 用户请求、相关状态、工具结果、错误、剩余预算 |
| Decision 决策 | 下一步应该做什么？ | 回答、调用工具、追问、请求审批、放弃 |
| Action 行动 | 对外执行什么？ | 搜索、读文件、查数据库、运行测试、发送请求 |
| Feedback 反馈 | 行动产生了什么结果？ | 数据、错误码、测试输出、权限拒绝 |
| State 状态 | 跨轮次需要保存什么？ | 已完成步骤、事实、候选结论、错误、成本 |
| Stop Rules 停止规则 | 什么时候必须结束？ | 成功、失败、超时、超预算、超步数、人工取消 |

最短的定义是：

> **Agent Loop 是一个由应用控制、由模型参与选择下一步动作、并通过环境反馈持续更新状态的执行循环。**

### 2.1 Goal 的来源与本层边界

用户不需要手工填写完整 Goal。自然语言请求会先经过上游的 Goal Intake / Planning：完成目标规范化、默认值与策略补全、必要澄清和子目标拆分，再把当前可执行子目标交给 Loop。

Loop 的职责是围绕当前子目标持续“观察 → 决策 → 行动 → 评估”，而不是自行改写用户的主 Goal、扩大任务范围或提升权限。Goal Intake、Clarification Gate、Goal Decomposer 和滚动规划的完整设计见[《如何定义目标与计划》](<03-如何定义目标与计划.md>)。

## 三、一次完整循环内部发生了什么

一轮 Loop 通常包含六个阶段：

### 3.1 构造本轮 Context

应用从 State、会话、检索结果和工具输出中，挑选本轮模型真正需要的信息：

```text
固定指令
+ 当前目标
+ 当前阶段和已知事实
+ 最近且相关的工具结果
+ 可用工具及参数 Schema
+ 权限、预算和停止约束
= 本轮 Context
```

Context 是工作集，不是数据库快照。它应该尽量小、相关、可信，并保留来源。

### 3.2 模型生成结构化决策

模型不应只输出一段无法解析的自然语言，而应返回有限的动作类型：

```json
{
  "action": "call_tool",
  "tool": "query_metrics",
  "arguments": {
    "service": "order-api",
    "window_minutes": 30
  },
  "reason": "日志显示数据库连接超时，需要检查连接池和依赖延迟"
}
```

`reason` 可用于追踪，但程序真正依赖的是经过 Schema 校验的 `action`、`tool` 和 `arguments`。

### 3.3 应用校验决策

在执行之前，程序检查：

- 动作类型是否允许；
- 工具是否注册；
- 参数是否满足 Schema；
- 当前身份是否有权限；
- 是否属于写操作或高风险动作；
- 是否需要人工审批；
- 是否超过步数、时间、Token 或费用预算。

模型表达的是“想做什么”，并不代表它“被允许这么做”。

### 3.4 工具执行动作

工具层完成真实操作，并返回统一结果：

```json
{
  "ok": true,
  "data": {
    "db_pool_wait_p95_ms": 1480,
    "db_connections_used": 100,
    "db_connections_max": 100
  },
  "error": null,
  "source": "metrics-prod-readonly",
  "observed_at": "2026-09-20T10:30:00+08:00"
}
```

工具输出是“不可信外部输入”的一种。即使工具调用成功，也要考虑内容是否过期、是否完整、是否含 Prompt Injection 或敏感数据。

### 3.5 更新 State 并评估进展

应用从结果中更新结构化状态，例如：

- 新确认的事实；
- 已调用过的工具和参数；
- 当前假设及证据；
- 错误和重试次数；
- 累计步骤、时间和费用；
- 是否已满足成功标准。

### 3.6 继续、暂停或停止

Loop 最终只能做三类控制决策：

```text
继续：还缺少信息，并且仍有安全、合理的下一步
暂停：需要用户补充信息或批准高风险动作
停止：目标完成、无法继续、达到限制或被取消
```

## 四、Loop 不是“模型在自己思考”

下面这个区别非常重要：

| 模型内部推理 | Agent Loop |
| --- | --- |
| 发生在一次模型调用内部 | 跨越多次模型调用和真实工具动作 |
| 外部应用通常看不到完整内部过程 | 应用可以记录每轮输入、动作和工具结果 |
| 不产生真实世界副作用 | 可以读取数据、修改文件、调用业务系统 |
| 由模型推理机制控制 | 由应用的循环、权限和停止条件控制 |

因此，“让模型多想一会儿”和“让 Agent 多运行几轮”不是同一件事。前者主要消耗模型推理预算，后者会增加工具调用、延迟、费用和真实副作用风险。

## 五、Loop 与相邻概念的边界

| 概念 | 谁决定下一步 | 是否动态使用工具 | 主要控制对象 |
| --- | --- | --- | --- |
| 单次模型调用 | 应用固定 | 否 | 一次输入输出 |
| Chain / Pipeline | 程序预先规定 | 可以，但顺序固定 | 一串固定步骤 |
| Workflow | 规则和程序 | 可以 | 业务流程、分支和事务 |
| **Agent Loop** | **模型在受限动作空间内选择** | **是** | **局部动态探索** |
| Agent Graph | 图、规则和模型共同控制 | 是 | 跨阶段状态、路由、暂停和恢复 |
| Agent Harness | 不定义业务目标 | 承载并约束工具 | 整个 Agent 的可靠执行环境 |

一句话区分：

- **Loop：**下一步做什么？
- **Graph：**整个任务按什么结构推进？
- **Runtime：**谁负责调度、持久化和恢复？
- **Harness：**如何让模型和工具安全、可控、可观测地运行？

# 第二部分：一个案例走完全程

> 学习目标：通过一条具体执行轨迹，看懂每轮 Context、Decision、Action、Feedback、State 和 Stop Rule 如何协作。

## 六、贯穿案例：诊断订单接口超时

用户请求：

> “订单接口从 10:00 开始明显变慢，帮我找出最可能的原因。只做诊断，不要修改生产环境。”

任务边界：

| 维度 | 内容 |
| --- | --- |
| 目标 | 找到有证据支持的最可能原因，并给出下一步建议 |
| 允许动作 | 查询只读日志、指标、部署记录和配置快照 |
| 禁止动作 | 修改配置、扩容、重启、回滚、执行生产写操作 |
| 成功标准 | 结论至少有两类证据支持，并说明不确定性 |
| 停止条件 | 完成、信息不足、工具不可用、超过 8 步、超过 5 分钟、用户取消 |

### 6.1 初始 State

```json
{
  "goal": "诊断订单接口从 10:00 开始变慢的原因",
  "scope": {
    "service": "order-api",
    "environment": "production",
    "read_only": true,
    "start_time": "2026-09-20T10:00:00+08:00"
  },
  "facts": [],
  "hypotheses": [],
  "tool_history": [],
  "errors": [],
  "step": 0,
  "max_steps": 8,
  "status": "running"
}
```

注意：State 保存任务事实和控制信息，不保存每轮完整 Prompt，也不把所有日志原文永久复制进去。大体积工具结果应保存为 Artifact，由 State 保存引用和摘要。

### 6.2 第 1 轮：先确认症状范围

**Observation**

```text
目标：诊断 order-api 从 10:00 开始变慢
限制：只读，不得修改生产
已知事实：无
可用工具：query_service_metrics、search_logs、get_deployments、read_config_snapshot
```

**Decision**

```json
{
  "action": "call_tool",
  "tool": "query_service_metrics",
  "arguments": {
    "service": "order-api",
    "from": "09:30",
    "to": "10:30",
    "metrics": ["request_rate", "latency_p95", "error_rate"]
  }
}
```

**Feedback**

```text
10:02 起 p95 从 220ms 上升到 2.8s；请求量无明显变化；错误率轻微上升。
```

**Evaluation**

排除“流量暴增”这一首要假设，但仍无法定位依赖、代码或资源层原因，继续循环。

### 6.3 第 2 轮：检查错误模式

模型根据指标决定搜索同一时间段的错误日志，而不是盲目重复查询指标。

**Feedback 摘要**

```text
日志中大量出现：Timeout acquiring connection from pool；
订单接口自身 CPU 和内存稳定。
```

**State 更新**

```json
{
  "facts": [
    "10:02 起延迟显著上升",
    "请求量无明显变化",
    "应用 CPU 与内存稳定",
    "数据库连接池获取连接超时"
  ],
  "hypotheses": [
    {
      "name": "数据库连接池耗尽",
      "confidence": 0.65,
      "evidence": ["连接池超时日志"]
    }
  ]
}
```

### 6.4 第 3 轮：寻找第二类证据

成功标准要求至少两类证据，Agent 不应看到一条日志就立刻下结论。它继续查询依赖指标：

```text
连接池使用量：100 / 100
连接等待 p95：1.48s
数据库 CPU：正常
慢查询：无明显增长
```

现在有两类独立证据：日志和连接池指标。假设置信度上升，但仍要解释“为什么从 10:02 突然发生”。

### 6.5 第 4 轮：检查时间相关变更

Agent 查询部署和配置变更记录：

```text
09:58 部署 order-api v3.14.2；
变更内容包含下游支付状态查询；
部署后单请求数据库连接持有时间从约 40ms 升至约 410ms。
```

### 6.6 第 5 轮：形成结论并停止

Agent 已满足成功标准：

- 症状时间与部署时间相邻；
- 日志显示连接池获取超时；
- 指标显示连接池满载且等待时间升高；
- CPU、内存、请求量和数据库慢查询没有同步异常；
- 新版本使连接持有时间显著增加。

最终输出应明确区分事实、推断和建议：

```text
最可能原因：v3.14.2 引入的支付状态查询延长了数据库连接持有时间，
导致连接池耗尽，进而推高订单接口延迟。

证据：
1. 09:58 部署，10:02 延迟开始上升；
2. 同期出现连接池获取超时日志；
3. 连接池持续 100/100，等待 p95 达 1.48s；
4. 单请求连接持有时间由约 40ms 升至约 410ms。

不确定性：尚未通过代码级 Trace 确认具体调用路径。
建议：由值班人员审核后决定是否回滚；本次任务没有执行任何生产变更。
```

应用随后执行终止检查：目标已满足、没有待执行动作、未越权，状态变为 `completed`。

## 七、这条轨迹为什么是一个合格的 Loop

| 要求 | 案例中的体现 |
| --- | --- |
| 每一步基于新观察 | 指标 → 日志 → 依赖指标 → 变更记录 |
| 没有重复无意义动作 | 每轮都在缩小假设空间 |
| 使用多源证据 | 日志、监控、部署、连接持有时间 |
| 权限边界明确 | 只读工具，禁止生产写操作 |
| 成功可验证 | 两类证据 + 不确定性说明 |
| 停止条件清晰 | 目标完成后停止，不继续“顺手修复” |

## 八、同一案例的失败轨迹

一个质量差的 Loop 可能这样运行：

```text
第 1 轮：看到“接口变慢” → 直接判断流量过大
第 2 轮：查询流量，发现正常 → 再次查询同一指标
第 3 轮：搜索大量无时间范围的日志 → Context 被噪声淹没
第 4 轮：看到连接超时 → 未经验证就建议重启数据库
第 5 轮：调用重启工具 → 越过“只做诊断”的权限边界
```

问题不在模型“不会推理”，而在系统没有提供：

- 明确目标和成功标准；
- 结构化 State 和已执行动作记录；
- 工具参数与时间范围约束；
- 只读权限；
- 重复检测；
- 高风险动作审批；
- 可靠的停止条件。

# 第三部分：核心设计

## 九、Context：每一轮给模型什么

### 9.1 Context 的推荐分层

| 层 | 内容 | 是否每轮都需要 |
| --- | --- | --- |
| 固定指令 | 角色、原则、输出契约、安全边界 | 通常需要 |
| 当前请求 | 用户目标、范围、约束 | 需要 |
| 结构化任务状态 | 已知事实、未决问题、步骤、预算 | 需要，但只选相关字段 |
| 最近交互 | 最近几轮决策和结果 | 按需 |
| 工具描述 | 本轮可用工具和 Schema | 需要，但只暴露允许的工具 |
| 检索内容 | 文档、知识、历史案例 | 按需检索 |
| Artifact 摘要 | 大文件、日志、测试输出的引用和摘要 | 按需 |
| Durable Memory | 已验证的长期用户偏好或事实 | 仅在相关且授权时 |

### 9.2 不要把完整历史当作 Context 策略

简单地把每次 Prompt、模型输出和工具结果全部追加到消息历史，会造成：

- Token 持续增长；
- 旧信息与新事实冲突；
- 模型关注无关细节；
- 工具返回中的恶意指令进入高权限上下文；
- 敏感信息被传播到不需要它的轮次；
- 调试时无法区分哪些内容真正影响了决策。

更合理的做法是：**State 保存结构化事实，Artifact 保存原始材料，Context Builder 每轮选择最相关的工作集。**

## 十、State：当前任务的跨轮状态

State 保存本次任务跨轮需要的事实与控制信息；任务可以持续很久，但这不自动使它成为跨任务 Memory。两者的存取边界见[信息分工](<05-State、RAG与Memory怎么分工.md>)。

State 至少包含五类信息：

```python
class LoopState:
    goal: str                  # 目标与成功标准
    facts: list               # 已验证事实及来源
    hypotheses: list          # 当前假设及证据
    actions: list             # 已执行动作和结果引用
    control: dict             # 步数、预算、超时、状态、审批
```

设计原则：

1. **事实与推断分开。**“连接池 100/100”是事实，“连接池耗尽由新版本导致”是推断。
2. **保存来源和时间。**尤其是实时指标、检索内容和外部系统数据。
3. **大对象只存引用。**日志文件、网页、代码仓库和长文档使用 Artifact ID。
4. **控制状态由程序写。**步骤、费用、权限和审批结果不能由模型任意覆盖。
5. **模型输出校验后再入 State。**非法或未经验证的内容不得变成任务事实。

## 十一、Decision：把自由生成限制为有限动作

推荐动作集合：

| 动作 | 含义 | 谁最终控制 |
| --- | --- | --- |
| `call_tool` | 请求调用一个工具 | 程序校验并执行 |
| `respond` | 已有足够信息，生成最终答复 | 程序做完成检查 |
| `ask_user` | 缺少用户才能提供的信息 | 程序暂停任务 |
| `request_approval` | 希望执行高风险动作 | 人工审批决定 |
| `handoff` | 转交给人或另一个受控流程 | 编排层路由 |
| `stop` | 明确无法继续或不应继续 | 程序记录原因并结束 |

模型不应直接返回诸如“我已经删除文件”“我已经完成退款”之类的事实。它只能提出动作请求，真实执行结果必须来自工具或业务系统。

## 十二、Action：工具设计决定 Loop 上限

一个可用工具应具备：

- 清晰名称和用途，避免多个工具语义重叠；
- 严格的输入 Schema、范围和枚举；
- 明确的只读或写入属性；
- 最小权限身份；
- 超时、错误码和可重试性说明；
- 写操作的幂等键；
- 统一、紧凑、可引用的输出；
- 可审计的调用记录。

反例：

```text
run_any_sql(sql: string)
```

更安全的设计：

```text
query_order_metrics(
    service: enum,
    from: datetime,
    to: datetime,
    metric_names: enum[],
    max_points: integer <= 1000
)
```

工具越宽泛，模型越容易误用；工具越贴近稳定业务能力，权限和测试越容易控制。

## 十三、Feedback：工具结果不是最终事实

工具结果进入下一轮前，需要处理：

1. **执行状态：**成功、失败、超时、取消或部分完成；
2. **数据校验：**类型、范围、必填字段和业务约束；
3. **来源信息：**系统、时间、版本和查询条件；
4. **大小控制：**截断、聚合、分页或保存为 Artifact；
5. **安全过滤：**敏感字段、恶意指令和不可信内容隔离；
6. **语义摘要：**只提取下一步判断真正需要的事实，同时保留原始引用。

“工具调用成功”只表示技术执行成功，不代表数据正确、足够、新鲜或与当前目标相关。

## 十四、Evaluation：怎样知道任务在前进

每轮之后至少进行三类检查：

### 14.1 动作级检查

- 工具是否按预期执行；
- 参数是否正确；
- 结果是否为空、冲突或过期；
- 是否发生可重试错误。

### 14.2 任务级检查

- 新结果是否减少了未知；
- 是否新增可验证事实；
- 当前假设是否更强或被推翻；
- 是否已经满足成功标准。

### 14.3 控制级检查

- 是否重复了相同动作；
- 是否超过步数、时间或费用预算；
- 是否触碰权限或数据边界；
- 用户是否取消；
- 是否需要暂停、升级或人工接管。

不要完全依赖同一个模型自评“我完成了”。更稳妥的方法是组合：

```text
确定性规则 + 工具返回的客观信号 + 必要时独立评估器 + 人工判断
```

## 十五、Stop Rules：退出条件比 Prompt 更重要

一个生产 Loop 至少要有以下退出原因：

| 原因 | 状态 | 后续 |
| --- | --- | --- |
| `goal_completed` | 成功 | 返回结果和证据 |
| `needs_user_input` | 暂停 | 等待用户补充后恢复 |
| `needs_approval` | 暂停 | 审批后继续或终止 |
| `max_steps_reached` | 受限失败 | 返回已完成内容和未决问题 |
| `timeout` | 受限失败 | 保存 checkpoint，可选择恢复 |
| `budget_exceeded` | 受限失败 | 降级或请求增加预算 |
| `tool_unavailable` | 失败/降级 | 换工具、稍后重试或人工处理 |
| `permission_denied` | 安全终止 | 不尝试绕过权限 |
| `cancelled` | 用户终止 | 立即停止后续动作 |
| `no_progress` | 失败/人工接管 | 防止重复调用和无限反思 |

### 15.1 如何检测 no progress

可以组合以下信号：

- 连续多轮没有新增事实；
- 重复调用同一工具和相同参数；
- 多次产生语义等价的动作；
- 假设置信度没有变化；
- 同一错误重复出现且重试策略未改变；
- 模型不断要求“再检查一次”却说不出新信息价值。

## 十六、错误、重试与恢复

### 16.1 不是所有错误都应该重试

| 错误类型 | 示例 | 推荐处理 |
| --- | --- | --- |
| 瞬时错误 | 限流、网络抖动、临时 5xx | 指数退避后有限重试 |
| 参数错误 | 时间格式错误、字段缺失 | 修正一次；仍失败则停止或人工 |
| 权限错误 | 无权读取生产日志 | 不重试，不绕过，返回权限问题 |
| 业务拒绝 | 订单状态不允许退款 | 不重试，解释业务原因 |
| 资源不存在 | 文件或对象不存在 | 核对路径/ID，必要时询问用户 |
| 非幂等写失败 | 请求结果不确定 | 先查执行记录，不能直接重放 |

### 16.2 checkpoint 保存什么

长任务可以在每个安全边界保存：

- 当前 State 版本；
- 已执行动作和外部操作 ID；
- 待审批动作；
- 已消耗预算；
- 当前工具和模型版本；
- 恢复时允许进入的下一状态。

checkpoint 只能帮助恢复 State，不能自动保证外部写操作只执行一次。写工具仍需要幂等键、执行记录和必要的补偿逻辑。

## 十七、安全：Loop 会放大权限，而不是只放大能力

安全设计至少包括：

- 工具白名单，而不是允许模型访问所有系统；
- 按任务动态下发最小权限；
- 读写分离，默认只读；
- 高风险动作必须显式审批；
- 工具结果按不可信输入处理；
- Secret 不进入模型 Context；
- 每轮限制数据量和可访问范围；
- 保留身份、参数、结果和审批记录；
- 预算和 kill switch 由应用控制；
- 工具描述、检索文档和网页内容不能覆盖系统指令。

# 第四部分：工程实现

## 十八、最小受控 Loop 伪代码

```python
def run_agent(task, user, tools, limits):
    state = initialize_state(task, user, limits)

    while state.status == "running":
        # 1. 应用先检查硬限制
        stop = check_limits(state)
        if stop:
            return finish(state, stop)

        # 2. 只为本轮构造最小 Context
        context = build_context(
            instructions=SYSTEM_RULES,
            goal=state.goal,
            facts=select_relevant_facts(state),
            recent_results=select_recent_results(state),
            available_tools=allowed_tools(user, state),
            remaining_budget=remaining_budget(state),
        )

        # 3. 模型只提出结构化动作请求
        proposal = model_decide(context, schema=AgentDecision)

        # 4. 程序做确定性校验
        decision = validate_decision(proposal, state, user, tools)

        if decision.type == "respond":
            if success_criteria_met(state, decision):
                return finish(state, "goal_completed", decision.answer)
            state.add_error("premature_finish")
            continue

        if decision.type == "ask_user":
            return pause(state, "needs_user_input", decision.question)

        if decision.type == "request_approval":
            return pause(state, "needs_approval", decision.action)

        if decision.type == "stop":
            return finish(state, decision.reason)

        # 5. 工具层执行并标准化结果
        result = execute_tool(
            decision.tool,
            decision.arguments,
            timeout=tool_timeout(decision.tool),
            idempotency_key=make_idempotency_key(state, decision),
        )

        # 6. 应用更新 State、记录 Trace 和 checkpoint
        state = update_state(state, decision, result)
        emit_trace(state, decision, result)
        save_checkpoint(state)

        # 7. 每轮检测是否真正取得进展
        if no_progress(state):
            return finish(state, "no_progress")
```

这段代码最重要的不是模型调用，而是模型调用前后的确定性控制。

## 十九、Decision Schema 示例

```python
from typing import Literal, Any
from pydantic import BaseModel, Field


class AgentDecision(BaseModel):
    type: Literal[
        "call_tool",
        "respond",
        "ask_user",
        "request_approval",
        "stop",
    ]
    tool: str | None = None
    arguments: dict[str, Any] = Field(default_factory=dict)
    answer: str | None = None
    question: str | None = None
    reason: str


def validate_decision(decision: AgentDecision, allowed: set[str]):
    if decision.type == "call_tool":
        if not decision.tool:
            raise ValueError("call_tool requires tool")
        if decision.tool not in allowed:
            raise PermissionError("tool is not allowed")
    return decision
```

Schema 只解决“格式是否合法”，不能替代权限、业务规则和副作用控制。

## 二十、推荐的实现顺序

### 20.1 第一阶段：先跑通一个只读 Loop

1. 选择一个边界明确、可人工验证的任务；
2. 只提供 2～4 个只读工具；
3. 定义成功标准和最大步数；
4. 保存每轮 Decision、Action 和 Feedback；
5. 用 20～50 个真实样例验证工具选择和停止行为。

### 20.2 第二阶段：加入结构化 State 和 Context Builder

1. 从消息历史中抽出事实、假设、动作和控制字段；
2. 大输出保存为 Artifact；
3. 每轮只选择相关信息进入 Context；
4. 为来源和时间建立统一格式；
5. 加入重复检测和 no-progress 退出。

### 20.3 第三阶段：加入暂停、审批和恢复

1. 为写操作分类风险；
2. 引入人工审批；
3. 为长任务保存 checkpoint；
4. 为写工具增加幂等键；
5. 测试崩溃发生在工具执行前、执行中和执行后的恢复行为。

### 20.4 第四阶段：把 Loop 放入 Graph 或业务 Workflow

当任务扩展为多个业务阶段时，不要继续把所有逻辑塞进一个大 Loop。将局部探索保留为节点内部 Loop，把审批、交易、跨系统状态和恢复交给 Graph / Workflow。

## 二十一、测试：至少覆盖三条主线

### 21.1 正常任务

```text
输入：信息充分、工具正常
验证：选择正确工具、参数正确、步数合理、结论有证据、按时停止
```

### 21.2 失败任务

```text
输入：工具超时、空结果、冲突数据、非法参数
验证：有限重试、能换策略、不伪造结果、不无限循环、保留失败原因
```

### 21.3 权限边界任务

```text
输入：用户要求执行未授权写操作，或工具结果诱导 Agent 泄露数据
验证：拒绝越权、不会绕过审批、不会把 Secret 放进 Context、留下审计记录
```

## 二十二、评测指标

| 维度 | 推荐指标 | 说明 |
| --- | --- | --- |
| 任务结果 | Task success rate | 是否完成用户真正的目标 |
| Groundedness | 有证据结论比例 | 结论是否能追溯到工具或可信来源 |
| 工具选择 | Tool selection accuracy | 是否选对工具 |
| 参数质量 | Argument validity rate | 参数是否通过 Schema 和业务校验 |
| 循环效率 | Steps to success | 成功任务用了多少步 |
| 重复程度 | Duplicate action rate | 是否反复做相同动作 |
| 停止质量 | Premature / late stop rate | 是否过早或过晚停止 |
| 恢复能力 | Recoverable run rate | 中断后能否从安全点继续 |
| 安全 | Unauthorized action rate | 越权动作必须趋近于零 |
| 成本与延迟 | Token、工具成本、p50/p95 延迟 | 质量必须与资源消耗一起评估 |

不要只评最终答案。最终答案正确，过程仍可能存在多余调用、越权尝试或不可接受的成本。

## 二十三、可观测：一条 Trace 应该看到什么

建议每轮记录：

```text
run_id / user_id / task_id
step / started_at / duration
context_version / prompt_version / model_version
available_tools / selected_action / validated_arguments
permission_decision / approval_id
tool_result_status / artifact_id / error_code
state_diff / tokens / cost
stop_reason
```

记录 Context 的版本和摘要，而不是无节制地复制敏感原文。Trace 既要支持调试，也要符合数据最小化和保留周期要求。

# 第五部分：边界与协作

## 二十四、什么时候适合 Agent Loop

适合的任务通常同时满足：

- 下一步确实依赖上一步结果；
- 工具数量有限且接口清楚；
- 目标可以验证；
- 行动空间可以被权限和预算约束；
- 任务容许一定延迟；
- 失败时可以安全停止或人工接管。

典型场景：

- 开放式资料搜索和研究；
- 代码阅读、诊断、修改和测试；
- 日志分析和故障排查；
- 个人助理中的跨工具查询；
- 数据探索和报告准备；
- Graph 某个节点内部的局部搜索或推理。

## 二十五、什么时候不应该使用 Agent Loop

| 场景 | 更合适的方案 | 原因 |
| --- | --- | --- |
| 翻译、总结、分类、抽取 | 单次模型调用 | 不需要持续行动 |
| 固定的检索后生成 | RAG Pipeline | 步骤可预先确定 |
| 确定性审批和交易 | Workflow / 后端代码 | 规则和事务比自主探索重要 |
| 高频、低延迟决策 | 规则、模型服务或专用系统 | 多轮 Loop 延迟和成本过高 |
| 无法验证的高风险决策 | 人工主导 | 错误后果不可接受 |
| 工具权限无法隔离 | 先完善权限体系 | Loop 会放大潜在副作用 |

决策原则：

> **如果程序可以提前知道每一步，就使用 Workflow；如果必须根据环境反馈动态选择下一步，才使用 Loop。**

## 二十六、什么时候从 Loop 升级为 Graph

出现以下信号时，应把大 Loop 拆成 Graph：

- 任务出现多个稳定业务阶段；
- 不同阶段有不同权限或负责人；
- 需要在某个节点暂停数小时或数天；
- 存在人工审批、并行分支或补偿流程；
- 失败后需要从特定阶段恢复；
- 不同分支有明确的服务等级或超时；
- 单一 Loop 的 Context 过大，难以测试和解释；
- 需要证明某些步骤一定按顺序发生。

推荐组合：

```text
Graph：接单 → 诊断 → 方案 → 审批 → 执行 → 验证
                  │
                  └─ “诊断”节点内部使用受限 Agent Loop
                     查指标 → 查日志 → 更新假设 → 补充证据 → 完成诊断
```

## 二十七、Loop、Graph 与 Harness 的组合方式

```text
用户 / 业务事件
        ↓
Agent Harness
  ├─ 身份、权限、沙箱、预算、审批
  ├─ 模型适配、工具执行、追踪、checkpoint
  └─ Runtime
       ├─ 简单任务：运行一个受控 Agent Loop
       └─ 复杂任务：调度 Agent Graph
              └─ 某些节点内部运行局部 Agent Loop
```

分工如下：

| 层 | 主要职责 | 不应承担 |
| --- | --- | --- |
| Loop | 根据反馈动态选择下一步 | 跨阶段业务流程治理 |
| Graph | 管理阶段、路由、并行、暂停和恢复点 | 替代工具安全和业务事务 |
| Runtime | 调度执行、并发、持久化和恢复 | 决定业务语义 |
| Harness | 权限、预算、审批、工具、追踪和可靠执行 | 替代模型能力和业务建模 |

## 二十八、常见 Loop 模式

### 28.1 Tool-use Loop

```text
观察 → 选工具 → 执行 → 读取结果 → 回答或继续
```

最常见，适合短任务和个人助理。

### 28.2 Plan-and-Execute

```text
生成粗计划 → 执行一步 → 根据结果修订计划 → 继续
```

适合多步骤但计划可能变化的任务。计划是可修改假设，不是不可违反的真理。

### 28.3 Hypothesis Loop

```text
提出假设 → 选择最有信息价值的检查 → 更新置信度 → 收敛
```

适合故障诊断、研究和数据分析。

### 28.4 Critique-and-Revise

```text
生成草稿 → 按明确标准评估 → 定向修改 → 达标后停止
```

适合代码、文档和结构化产物。必须限制修改轮数，评估标准要尽量客观。

### 28.5 Human-in-the-loop

```text
模型提出动作 → 程序识别风险 → 暂停 → 人工批准/拒绝 → 恢复
```

人工不是失败兜底，而是系统设计中的正式状态。

## 二十九、常见误区速查

| 误区 | 正确认识 |
| --- | --- |
| Agent Loop 就是无限调用模型 | Loop 必须由应用控制，并有硬停止条件 |
| 模型说完成就是真的完成 | 完成要用成功标准和客观证据验证 |
| 把全部历史发给模型最保险 | 应使用结构化 State 和选择性 Context |
| 工具调用成功就说明任务成功 | 技术成功、数据有效和任务完成是三件事 |
| 多反思几轮一定更准确 | 反思可能重复放大错误，必须有标准和上限 |
| 工具越多 Agent 越强 | 工具越多，选择、权限和测试复杂度越高 |
| checkpoint 可以防止重复写入 | checkpoint 不等于 exactly-once，写操作仍需幂等 |
| Loop 可以替代业务后端 | 权限、事务和业务事实仍由传统系统负责 |
| 所有复杂任务都应使用多 Agent | 先用受控单 Agent；只有隔离或并行价值明确时再拆分 |
| Graph 比 Loop 更高级 | 二者解决不同层次问题，经常组合使用 |

## 三十、上线前检查清单

### 目标与边界

- [ ] 目标、范围和成功标准是否明确？
- [ ] 哪些动作允许，哪些禁止，是否写进程序策略？
- [ ] 无法完成时如何停止或人工接管？

### Context 与 State

- [ ] Context 是否按轮次选择，而不是无限追加？
- [ ] 事实、推断、控制状态和原始 Artifact 是否分开？
- [ ] 外部内容是否保留来源和时间？
- [ ] Secret 和无关敏感信息是否被排除？

### 工具与执行

- [ ] 工具是否有严格 Schema、超时和标准错误？
- [ ] 是否默认最小权限和只读？
- [ ] 写操作是否幂等并可审计？
- [ ] 高风险动作是否需要审批？

### Loop 控制

- [ ] 是否有最大步数、总超时和费用预算？
- [ ] 是否检测重复动作和 no progress？
- [ ] 是否支持取消、暂停和必要的恢复？
- [ ] 每种 stop reason 是否有清晰的用户反馈？

### 评测与运营

- [ ] 是否覆盖正常、失败和权限边界样例？
- [ ] 是否评估过程，而不仅是最终答案？
- [ ] 是否能查看每轮 Trace 和 State diff？
- [ ] 模型、Prompt、工具和策略是否可版本化与回滚？

## 理解检查

如果能够回答下面问题，就已经掌握 Agent Loop 的核心：

1. 为什么一次模型调用不等于 Agent Loop？
2. Observation、State 和 Context 分别是什么？
3. 为什么模型只能提出工具调用请求，而不能自行认定工具已经执行？
4. 一个 Loop 至少需要哪些停止条件？
5. 如何检测 Agent 虽然在运行，却没有取得进展？
6. 为什么 checkpoint 不能替代幂等？
7. 什么任务适合 Loop，什么任务更适合 Workflow？
8. 什么时候应把一个大 Loop 拆成 Agent Graph？
9. 模型、Loop、Graph、Runtime 和 Harness 各自负责什么？
10. 如何证明一个 Loop 不仅答案正确，而且过程安全、成本合理？

## 结语

Agent Loop 的真正价值，不是让模型“自主得更久”，而是让它在每次获得新信息后，都能选择一个有价值、可验证、权限允许的下一步。

一个成熟的 Loop 应做到：

```text
目标明确
  + Context 精准
  + State 结构化
  + 动作有限且可校验
  + 工具最小权限
  + 每轮有进展
  + 结果可验证
  + 随时可以安全停止
```

当局部探索需要更强控制时，把 Loop 放入 Graph；当真实执行需要更高可靠性时，由 Harness 提供权限、预算、审批、追踪和恢复。这样，模型的不确定判断才会成为系统能力，而不是系统风险。
