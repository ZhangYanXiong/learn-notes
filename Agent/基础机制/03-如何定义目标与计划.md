## 一页结论

1. **用户只需要表达自然意图。**系统通过页面与会话上下文、业务默认值、安全策略和只读工具形成结构化 Goal。
2. **Goal Normalization 与 Goal Decomposition 是两个阶段。**前者明确要实现什么，后者决定需要解决哪些可验证问题。
3. **低风险歧义由系统处理，高影响且无法安全推断的歧义才询问用户。**
4. **Plan 不是 Goal 的组成部分。**Goal 相对稳定；Plan 是由 Goal 与 State 派生、可以版本化重建的执行方案。
5. **Subgoal 是 Goal 与 Plan 的桥梁。**Plan 组织 Subgoal 的依赖、顺序、状态和替代关系，而不是预写一串工具调用。
6. **Replan 只能改变路线，不能静默改变目的地。**范围扩大、风险提升、成功标准变化和权限提升属于 Goal 变更。
7. **Plan 执行完不等于任务成功。**最终完成仍由 Goal 的成功标准和客观证据判断。
8. **Plan 应由 Plan Controller 持有。**Planner 只提出候选计划；Controller 控制创建输入、计划校验、生命周期、调度、Subgoal 输入输出和 Replan。

# 第一部分：Goal Intake——从自然语言到结构化 Goal

> **归属说明：**目标规范化和拆分属于 Graph / Planning / Orchestration 层。产品与 API 层提供用户、页面和会话上下文；Harness 注入权限、预算和执行策略；Graph 把稳定 Goal 拆成阶段和子目标；Loop 只执行当前子目标。

## 一、用户不应该负责填写完整 Goal

Agent Graph 的输入经常是一句自然语言、邮件、工单或业务事件。它们不能直接成为可执行图的可信 State；在进入正式执行之前，需要先经过 Goal Intake，把模糊意图变成可验证、可约束、可路由的任务契约。这不意味着用户每次都要填写一张复杂表单。正常的产品体验应该是：

```text
用户自然语言
   ↓
目标规范化
   ↓
补充上下文、默认值和安全策略
   ↓
判断是否存在必须澄清的高影响歧义
   ↓
形成结构化 Goal
   ↓
拆分为可验证的子目标
   ↓
Agent Loop 动态执行
```

用户只负责表达真实意图，例如：

> “帮我看看订单接口为什么慢。”

应用负责把它变成 Agent 可以执行和验证的任务契约。一个实际 Goal 通常来自多种信息源：

```text
Goal
= 用户请求
+ 当前会话上下文
+ 用户在界面中选中的对象
+ 业务默认值
+ 组织安全策略
+ 已授权的用户偏好
+ 当前可用工具
+ 必要且可追踪的模型推断
```

例如，系统可以自动形成：

| Goal 字段 | 值 | 来源 |
| --- | --- | --- |
| 目标 | 定位订单接口延迟升高的最可能原因 | 从用户请求抽取 |
| 服务 | `order-api` | 服务名称映射或当前页面对象 |
| 环境 | 当前控制台选择的环境 | 页面上下文 |
| 时间范围 | 最近 30 分钟 | 诊断任务默认值 |
| 权限 | 只读 | 安全策略 |
| 交付物 | 原因、证据、不确定性和建议 | 诊断任务模板 |
| 成功标准 | 至少两类独立证据支持结论 | 业务评测标准 |
| 执行限制 | 最多 8 步、5 分钟 | Runtime 策略 |

关键要求是：每个自动补全字段都应记录来源。系统需要知道它是用户明确提供的、从当前页面读取的、由规则默认的，还是模型推断的。

## 二、目标规范化与目标拆分是两个阶段

这两个过程经常被混在一起：

| 阶段 | 回答的问题 | 产物 |
| --- | --- | --- |
| Goal Normalization 目标规范化 | 用户真正想得到什么？范围和约束是什么？ | 稳定的 `GoalSpec` |
| Goal Decomposition 目标拆分 | 为了完成目标，需要依次解决哪些问题？ | 可执行、可验证的子目标 |

不推荐让模型读到一句自然语言后，直接生成一长串工具调用。这样会跳过范围、权限、成功标准和停止条件，后面的每一步都建立在未经验证的假设上。

正确顺序是：

```text
自然语言 → GoalSpec → 子目标 / 里程碑 → 当前子目标的 Tool Loop
```

## 三、Goal Normalizer：把自然语言变成候选任务契约

Goal Normalizer 可以由模型完成语义抽取，但它输出的只是**候选结构**，仍然要经过程序校验和策略补全：

```python
from typing import Any, Literal
from pydantic import BaseModel, Field


class ValueWithSource(BaseModel):
    value: Any | None = None
    source: Literal[
        "user",
        "ui_context",
        "session_context",
        "policy_default",
        "tool",
        "model_inference",
    ]
    confidence: float = Field(ge=0.0, le=1.0)


class OpenQuestion(BaseModel):
    field: str
    reason: str
    impact: Literal["low", "medium", "high"]
    has_safe_default: bool
    can_be_discovered: bool


class GoalSpec(BaseModel):
    objective: str
    deliverables: list[str]
    scope: dict[str, ValueWithSource]
    constraints: list[str]
    success_criteria: list[str]
    assumptions: list[ValueWithSource]
    unresolved_questions: list[OpenQuestion]
    limits: dict[str, int] = Field(default_factory=dict)
```

对于“帮我看看订单接口为什么慢”，模型可能先输出：

```json
{
  "objective": "定位订单接口延迟升高的最可能原因",
  "deliverables": ["原因", "支持证据", "不确定性", "处理建议"],
  "scope": {
    "service": {
      "value": "order-api",
      "source": "model_inference",
      "confidence": 0.82
    },
    "environment": {
      "value": null,
      "source": "model_inference",
      "confidence": 0.0
    }
  },
  "constraints": [],
  "success_criteria": [],
  "assumptions": [],
  "unresolved_questions": [
    {
      "field": "environment",
      "reason": "不同环境的数据和权限不同",
      "impact": "high",
      "has_safe_default": false,
      "can_be_discovered": true
    }
  ]
}
```

随后由确定性程序加入不能由模型自行决定的内容：

```python
goal.constraints.extend([
    "默认只读",
    "禁止未经审批的生产变更",
])

goal.success_criteria.extend([
    "至少使用两类独立证据",
    "区分事实和推断",
    "说明仍未确认的信息",
])

goal.limits = {
    "max_steps": 8,
    "timeout_seconds": 300,
}
```

这里的责任边界是：

- **模型：**理解自然语言、抽取候选目标、识别歧义；
- **应用：**读取页面和会话上下文、补充默认值、执行安全策略；
- **工具：**发现能够从外部系统确认的信息；
- **用户：**处理系统无法安全决定的高影响问题。

## 四、Clarification Gate：不要缺字段就询问用户

缺失信息应分成三类：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 可以安全默认 | 输出格式未指定 | 采用产品默认值，记录假设 |
| 可以通过工具发现 | 服务负责人、最近部署时间 | 使用只读工具查询 |
| 必须由用户决定 | 两个同名系统、不可逆写操作的目标对象 | 暂停并询问或请求批准 |

只有同时满足以下条件时，才应打断用户：

```python
def should_ask_user(question: OpenQuestion) -> bool:
    return (
        question.impact == "high"
        and not question.has_safe_default
        and not question.can_be_discovered
    )
```

实际系统还应考虑：

- 不同答案是否会显著改变最终结果；
- 做错后的代价是否高于询问成本；
- 是否涉及生产环境、敏感数据、付款、删除或外部沟通；
- 当前用户是否有权做出这个选择；
- 能否先执行安全、可逆、只读的步骤缩小问题范围。

核心原则：

> **低风险歧义由系统处理，高影响且无法安全推断的歧义才交给用户。**

采用默认值时，不一定每次都要弹窗确认，但应让用户能够看到和纠正关键假设。例如：“我将按当前选中的生产环境、最近 30 分钟、只读模式进行诊断。”

## 五、Goal Decomposer：拆成结果，而不是拆成工具调用

完成 Goal Normalization 后，再把总目标拆成可验证的里程碑。以订单接口诊断为例：

```text
总目标：定位订单接口变慢的最可能原因

子目标 1：确认异常是否真实存在
子目标 2：确定异常发生的范围和时间
子目标 3：形成候选原因假设
子目标 4：为主要假设收集独立证据
子目标 5：检查重要的竞争假设
子目标 6：形成诊断结论和建议
```

不推荐这样拆：

```text
1. 调用 query_metrics
2. 调用 search_logs
3. 调用 get_deployments
```

因为这只是预设工具顺序，没有表达每一步要解决什么问题，也无法判断什么时候应该跳过、重复或替换工具。

一个子目标可以使用以下结构：

```python
class SubGoal(BaseModel):
    id: str
    objective: str
    depends_on: list[str]
    completion_criteria: list[str]
    allowed_tools: list[str]
    risk: Literal["read_only", "reversible_write", "irreversible"]
    status: Literal["pending", "ready", "running", "completed", "blocked", "cancelled"]
```

示例：

```json
{
  "id": "validate_root_cause",
  "objective": "验证最可能的根因",
  "depends_on": ["establish_symptoms", "generate_hypotheses"],
  "completion_criteria": [
    "至少有两类独立证据",
    "主要竞争假设已经被检查",
    "证据时间与异常时间一致"
  ],
  "allowed_tools": [
    "search_logs",
    "query_metrics",
    "get_deployments"
  ],
  "risk": "read_only",
  "status": "pending"
}
```

好的子目标应该满足：

1. 描述需要得到的结果，而不是指定某次工具调用；
2. 可以独立判断完成、失败或阻塞；
3. 有明确依赖、允许使用的工具和权限边界；
4. 足够小，能够在有限 Loop 中完成；
5. 完成后能减少总目标中的未知，而不是只增加更多文本。

## 六、使用滚动规划，而不是一次规划到底

任务刚开始时，Agent 对环境了解最少。此时生成十几步详细计划，很容易让后面的步骤建立在错误假设上。

更稳妥的方法是“粗粒度里程碑 + 近期步骤细化”：

```text
先生成稳定里程碑
        ↓
选择当前可执行子目标
        ↓
只细化当前子目标附近的行动
        ↓
在子目标内部运行受限 Tool Loop
        ↓
根据新结果更新事实、假设和计划
        ↓
完成、修改、增加或取消后续子目标
```

例如，初始计划只需要是：

```text
1. 确认症状
2. 定位原因
3. 输出结论
```

当 Agent 发现数据库连接池异常后，再把“定位原因”细化为：

```text
2.1 检查连接池使用量和等待时间
2.2 检查数据库负载和慢查询
2.3 检查近期部署和配置变更
2.4 验证变更与连接持有时间的关系
```

主 Goal 和安全约束应保持稳定；模型可以根据证据调整子目标，但不能静默扩大任务范围、修改成功标准或提升自身权限。

## 七、推荐的 Goal Intake 架构

```text
用户请求
   ↓
Goal Normalizer
抽取目标、范围、交付物和歧义
   ↓
Context / Policy Enricher
补充页面上下文、默认值、权限、预算和禁止事项
   ↓
Clarification Gate
只处理高影响且无法安全推断的问题
   ↓
Goal Decomposer
生成带完成标准的子目标
   ↓
Executor Loop
执行当前子目标
   ↓
Evaluator
验证结果，更新计划或停止
```

这套架构最终应该提供这样的用户体验：

> 用户只表达自然目标；系统自动形成 Goal 和初步计划，使用安全默认值或只读工具补齐信息，并且只在真正影响结果、安全或权限的地方向用户提问。

# 第二部分：Plan——Goal 的执行方案，而不是 Goal 本身

Goal 和 Plan 紧密相连，但不应该混成一个对象。推荐的概念链路是：

```text
User Intent
    ↓ 目标规范化
Goal：要实现什么、边界是什么、怎样算成功
    ↓ 规划
Plan：准备通过哪些子目标和依赖关系实现
    ↓ 调度
Current Subgoal：当前需要完成什么局部结果
    ↓ Loop
Action：这一轮具体做什么
    ↓
Observation：环境返回了什么
    ↓
更新 State，继续执行或重建 Plan
```

## 八、Goal 与 Plan 的责任边界

| 维度 | Goal | Plan |
| --- | --- | --- |
| 回答的问题 | 要达到什么结果？ | 准备怎样达到结果？ |
| 主要内容 | 目标、范围、约束、交付物、成功标准 | 子目标、顺序、依赖、候选路线和当前进度 |
| 稳定性 | 相对稳定 | 可以根据观察动态调整 |
| 变更来源 | 用户明确修改或业务规则变更 | Planner 根据新证据重新规划 |
| 完成判断 | 成功标准是否满足 | 计划步骤和子目标是否完成、取消或被替换 |
| 权限 | 定义不可跨越的权限边界 | 只能在 Goal 和策略允许的范围内选路线 |

一句话区分：

> **Goal 决定方向和终点，Plan 决定当前路线。**

例如：

```text
Goal：
找出订单接口变慢的最可能原因，至少提供两类独立证据，
只读诊断，不修改生产环境。
```

初始 Plan 可能是：

```text
1. 确认异常范围和开始时间
2. 检查流量与应用资源
3. 搜索错误日志
4. 检查依赖指标和近期部署
5. 验证主要假设并形成结论
```

如果第一轮发现异常只发生在华东地域，Plan 可以改成：

```text
1. 比较不同地域的延迟和错误率
2. 检查华东地域网络与依赖指标
3. 检查该地域的部署和配置差异
4. 验证最可能原因并形成结论
```

Plan 已改变，但 Goal、只读约束和成功标准没有改变。这正是 Plan 必须独立保存的原因。

## 九、Subgoal 是 Goal 与 Plan 之间的桥梁

Plan 不是低层工具调用清单，而是对子目标的组织：

```text
Goal
└── Plan v3
    ├── Subgoal A：确认异常范围
    ├── Subgoal B：生成候选原因
    ├── Subgoal C：验证最可能原因
    └── Subgoal D：形成结论和建议
```

每个 Subgoal 是一个局部、可验证的小目标；多个 Subgoal 的顺序、依赖、状态和替代关系共同构成 Plan。

```text
Goal：最终成功标准
Plan：子目标的组织方式
Subgoal：当前阶段要产出的局部结果
Loop：完成当前子目标的动态探索过程
Action：Loop 某一轮执行的具体动作
```

因此下面两种表示并不等价：

```text
好的 Plan：
确认症状 → 形成假设 → 验证根因 → 输出结论

脆弱的工具脚本：
调用 metrics → 调用 logs → 调用 deployments → 生成文本
```

前者允许 Planner 根据证据选择、跳过或替换工具；后者把尚未观察到的信息提前假定为固定路线。

## 十、在 State 中分开保存 Goal 和 Plan

推荐的数据结构：

```python
state = {
    "goal": {
        "version": 1,
        "objective": "定位订单接口变慢的原因",
        "constraints": ["只读", "不得修改生产"],
        "success_criteria": [
            "至少有两类独立证据",
            "说明仍然存在的不确定性",
        ],
    },

    "plan": {
        "version": 3,
        "created_from_goal_version": 1,
        "subgoals": [
            {
                "id": "confirm_scope",
                "objective": "确认异常范围",
                "status": "completed",
                "completion_evidence": ["artifact://metrics/region-comparison"],
            },
            {
                "id": "validate_cause",
                "objective": "验证最可能原因",
                "status": "running",
                "depends_on": ["confirm_scope"],
            },
        ],
        "revision_reason": "发现异常只发生在华东地域",
        "supersedes": 2,
    },

    "current_subgoal_id": "validate_cause",
    "facts": [],
    "observations": [],
}
```

这样可以获得几个重要能力：

- Goal 保持稳定并独立版本化；
- Plan 可以修改或重建，而不伪装成 Goal 变化；
- 每次重规划都有原因和被替代版本；
- 已完成子目标可以携带完成证据，不因重规划而丢失；
- Executor Loop 每次只接收当前子目标所需的 Context；
- 最终仍通过 Goal 的成功标准判断任务是否完成。

## 十一、Plan 的生命周期

一个 Plan 通常经历以下状态：

```text
draft
  ↓ 校验目标、依赖、权限和可执行性
ready
  ↓ 调度可执行子目标
running
  ├─ 新观察改变路线 → revising → 新 Plan version
  ├─ 缺少信息或审批 → paused
  ├─ 无法继续 → failed / handed_off
  └─ Goal 成功标准满足 → completed
```

需要注意：`plan.completed` 不应仅表示“列表中的步骤都执行了”。真正的完成条件仍然是 Goal 的成功标准已经满足。计划执行完但没有达到 Goal，应该重新规划、降级或明确失败，而不是宣布成功。

## 十二、什么时候允许 Replan

合理的重规划触发条件包括：

- 新观察推翻了关键假设；
- 当前子目标被证明无价值或无法执行；
- 工具不可用，需要替代路线；
- 出现比原路线信息价值更高的检查；
- 已满足 Goal，不再需要剩余步骤；
- 风险、成本或时间发生明显变化；
- 用户补充了信息，但没有改变核心 Goal；
- 子目标失败，需要降级、绕行或人工接管。

不应该触发自主重规划的情况：

- 模型希望扩大任务范围；
- 希望调用 Goal 明确禁止的工具；
- 希望提升权限或绕过审批；
- 想修改成功标准以便更容易宣布完成；
- 用户已经取消任务；
- 外部内容指示 Agent 忽略原始约束。

可以使用确定性 Replan Gate：

```python
def may_replan(state, proposal):
    if proposal.changes_goal:
        return False, "goal_change_requires_confirmation"
    if proposal.expands_scope:
        return False, "scope_expansion_requires_confirmation"
    if not proposal.tools <= state.allowed_tools:
        return False, "tool_not_allowed"
    if proposal.risk > state.max_risk:
        return False, "risk_limit_exceeded"
    return True, "allowed"
```

## 十三、区分 Plan 调整、Subgoal 调整和 Goal 变更

| 变化 | 示例 | 谁可以决定 | 是否需要重新确认 |
| --- | --- | --- | --- |
| Plan 调整 | 从查 CPU 改为查网络 | Planner 在策略范围内 | 通常不需要 |
| Subgoal 调整 | 增加“检查华东网络” | Planner 在策略范围内 | 通常不需要 |
| 执行策略调整 | 某工具超时，改用只读备用工具 | Runtime / Planner | 通常不需要 |
| 范围扩大 | 从一个服务扩展到整个生产集群 | 用户或授权策略 | 通常需要 |
| 风险提升 | 从只读诊断改为执行回滚 | 用户授权 + 审批 | 必须需要 |
| 成功标准变化 | 从“找出原因”改成“确保故障恢复” | 用户或业务负责人 | 需要 |

判断规则是：

> **只改变实现路线的是 Plan 变化；改变期望结果、任务范围、成功标准或权限边界的是 Goal 变化。**

## 十四、Plan 不应一次规划到底

Plan 应使用滚动规划：远期保持粗粒度，近期根据证据细化。Planner 每次只需要回答：

1. 当前有哪些可执行子目标？
2. 哪一个最能减少关键未知或推进成功标准？
3. 完成它需要哪些输入、权限和工具？
4. 什么证据能够证明它完成？
5. 执行后是否需要更新后续 Plan？

框架无关的规划伪代码：

```python
def plan_or_replan(state):
    proposal = planner.generate(
        goal=state.goal,
        facts=state.facts,
        current_plan=state.plan,
        available_tools=state.allowed_tools,
        remaining_budget=state.remaining_budget,
    )

    validate_plan_schema(proposal)
    validate_dependencies(proposal)
    validate_completion_criteria(proposal)
    allowed, reason = may_replan(state, proposal)

    if not allowed:
        return pause_or_reject(state, reason)

    proposal.version = state.plan.version + 1
    proposal.supersedes = state.plan.version
    proposal.created_from_goal_version = state.goal.version
    return activate_plan(state, proposal)
```

## 十五、怎样评估 Plan 的质量

Plan 质量不等于步骤越多越好。可以从以下方面评估：

| 维度 | 检查问题 |
| --- | --- |
| Goal alignment | 每个子目标是否直接推进某项成功标准？ |
| Executability | 子目标是否具有所需输入、工具和权限？ |
| Verifiability | 每个子目标是否有客观完成证据？ |
| Dependency correctness | 前后依赖是否真实存在，是否遗漏必要前置条件？ |
| Efficiency | 是否存在低信息价值、重复或可以并行的步骤？ |
| Adaptability | 新证据出现时，是否能局部修改而非全部推倒重来？ |
| Safety | 是否保持在 Goal 和策略允许的范围内？ |
| Stop awareness | Goal 已完成时，是否会取消不再必要的剩余步骤？ |

生产中可跟踪：计划修改次数、无效子目标比例、重复动作率、完成前平均 Plan 版本数、因权限拒绝导致的重规划率，以及 Plan 完成但 Goal 未完成的比例。

# 第三部分：Plan Controller——控制创建、执行与输入输出

> 核心原则：**模型提出 Plan，Controller 持有 Plan；模型提出 Action，Runtime 决定是否执行。**

## 十六、为什么需要 Plan Controller

如果应用直接执行模型生成的计划，模型实际上同时拥有了目标解释、计划生成、权限选择、执行调度和完成判定权。这会产生几个问题：

- Planner 可能看到不必要或不可信的数据；
- 模型可能创建系统不支持的 Subgoal；
- 计划可能包含不存在的依赖、越权工具或不可验证步骤；
- 模型可能跳过依赖、扩大范围或提升风险；
- Executor 的自然语言输出可能被直接当成完成事实；
- Replan 可能借机修改 Goal、成功标准或权限边界。

Plan Controller 是应用中的确定性控制层：

```text
Goal + State
    ↓
Plan Controller 构造 Planner Input
    ↓
Planner 生成 PlanProposal
    ↓
Plan Controller 校验 / 必要时请求审批
    ↓
Active Plan
    ↓
Scheduler 选择 Subgoal
    ↓
Controller 构造 Subgoal Input
    ↓
Executor Loop 执行
    ↓
Controller 校验 Subgoal Output 和证据
    ↓
更新 Plan / Replan / Pause / Stop
```

Plan Controller 不负责替代模型推理，而是控制模型能够看到什么、提出什么，以及什么结果可以进入真实执行状态。

## 十七、控制 Plan 的创建

### 17.1 控制 Planner Input

Planner 不应直接接收完整聊天历史、所有 State 字段和全部工具。Controller 应构造最小、相关、可信的规划输入：

```python
class PlannerInput(BaseModel):
    goal: GoalSpec
    known_facts: list[Fact]
    current_plan: Plan | None

    allowed_subgoal_types: list[str]
    allowed_tools: list[str]

    max_subgoals: int
    max_depth: int
    max_parallelism: int

    remaining_steps: int
    remaining_budget: float

    required_milestones: list[str]
    forbidden_actions: list[str]
```

例如：

```python
planner_input = PlannerInput(
    goal=state.goal,
    known_facts=select_verified_facts(state),
    current_plan=state.current_plan,
    allowed_subgoal_types=[
        "collect_evidence",
        "validate_hypothesis",
        "generate_report",
    ],
    allowed_tools=[
        "query_metrics",
        "search_logs",
        "get_deployments",
    ],
    max_subgoals=6,
    max_depth=2,
    max_parallelism=2,
    remaining_steps=state.remaining_steps,
    remaining_budget=state.remaining_budget,
    required_milestones=[
        "确认异常范围",
        "验证最可能原因",
        "形成有证据的结论",
    ],
    forbidden_actions=[
        "修改生产配置",
        "重启服务",
        "执行回滚",
    ],
)
```

这样，Planner 的自由度由应用明确限定，而不是由 Prompt 的模糊描述决定。

### 17.2 控制 Planner Output

Planner 只能生成结构化候选计划，不能直接创建 Active Plan：

```python
class SubGoalProposal(BaseModel):
    id: str
    type: Literal[
        "collect_evidence",
        "validate_hypothesis",
        "generate_report",
    ]
    objective: str
    depends_on: list[str]
    input_schema: dict
    output_schema: dict
    completion_criteria: list[str]
    requested_tools: list[str]
    risk: Literal[
        "read_only",
        "reversible_write",
        "irreversible",
    ]


class PlanProposal(BaseModel):
    subgoals: list[SubGoalProposal]
    assumptions: list[str]
    estimated_cost: float
    revision_reason: str | None = None
```

这里要区分：

```text
PlanProposal：模型建议怎样做
Active Plan：程序已经校验并批准执行的计划
```

### 17.3 校验后才能激活

```python
def validate_plan(proposal: PlanProposal, policy: PlanPolicy):
    if len(proposal.subgoals) > policy.max_subgoals:
        raise ValueError("too_many_subgoals")

    ensure_unique_ids(proposal)
    ensure_dependencies_exist(proposal)
    ensure_no_dependency_cycle(proposal)

    for subgoal in proposal.subgoals:
        if subgoal.type not in policy.allowed_subgoal_types:
            raise ValueError("subgoal_type_not_allowed")

        if not set(subgoal.requested_tools) <= policy.allowed_tools:
            raise PermissionError("tool_not_allowed")

        if not subgoal.completion_criteria:
            raise ValueError("completion_criteria_required")

        if risk_score(subgoal.risk) > risk_score(policy.max_risk):
            raise PermissionError("risk_exceeds_policy")

    ensure_goal_alignment(proposal, policy.goal)
    ensure_within_budget(proposal, policy)
```

至少要检查：

- ID 是否唯一，依赖是否存在且无环；
- 是否存在能够开始执行的 Subgoal；
- Subgoal 是否属于允许类型；
- 是否有客观完成标准；
- 工具是否在白名单内；
- 风险、深度、并行数和预算是否合规；
- 是否扩大 Goal 范围或修改成功标准。

## 十八、控制生命周期与执行调度

### 18.1 Plan 状态机

```text
DRAFT
  ↓ 校验通过
VALIDATED
  ↓ 自动批准或人工批准
APPROVED
  ↓
ACTIVE
  ├─ PAUSED
  ├─ REPLANNING → 新 Plan 版本
  ├─ COMPLETED
  ├─ FAILED
  └─ CANCELLED
```

状态迁移由 Controller 控制：

```python
ALLOWED_TRANSITIONS = {
    "draft": {"validated", "rejected"},
    "validated": {"approved", "rejected"},
    "approved": {"active"},
    "active": {
        "paused",
        "replanning",
        "completed",
        "failed",
        "cancelled",
    },
    "paused": {"active", "cancelled"},
    "replanning": {"active", "failed", "cancelled"},
}
```

模型可以建议暂停、完成或重规划，但不能直接改写生命周期状态。

### 18.2 Scheduler 只从 Ready Subgoal 中选择

```python
def get_ready_subgoals(plan: Plan) -> list[SubGoal]:
    completed = {
        item.id
        for item in plan.subgoals
        if item.status == "completed"
    }

    return [
        item
        for item in plan.subgoals
        if item.status == "pending"
        and set(item.depends_on) <= completed
    ]
```

简单任务可以使用确定性调度：

```python
def select_next(ready: list[SubGoal]) -> SubGoal:
    return min(
        ready,
        key=lambda item: (
            item.priority,
            risk_score(item.risk),
            estimated_cost(item),
            -information_gain(item),
        ),
    )
```

如果使用模型辅助调度，模型也只能从 Controller 已经判定为 Ready 的候选项中选择，不能绕过依赖关系。

## 十九、控制 Subgoal 的输入与输出

### 19.1 Subgoal Input

当前 Executor 不需要看到全部 Goal、Plan 历史和所有工具：

def build_subgoal_input(subgoal, state):

### 19.2 Subgoal Output

Executor 输出同样需要结构化：

```python
class SubGoalOutput(BaseModel):
    status: Literal[
        "candidate_completed",
        "needs_more_information",
        "blocked",
        "failed",
    ]
    facts_discovered: list[Fact]
    evidence: list[Evidence]
    artifacts_created: list[str]
    unresolved_questions: list[str]
    recommended_next_step: str | None
    side_effect_receipts: list[str]
```

其中 `candidate_completed` 只是 Executor 的建议。Controller 仍需依次执行：

```text
Schema 校验
  → 来源与 Artifact 校验
  → 权限和副作用凭证校验
  → Completion Criteria 校验
  → 更新 State 与 Plan
```

```python
def validate_subgoal_output(subgoal, output, state):
    validate_fact_sources(output.facts_discovered)
    validate_artifact_ids(output.artifacts_created)
    validate_side_effect_receipts(output.side_effect_receipts)

    assessment = evaluate_criteria(
        criteria=subgoal.completion_criteria,
        evidence=output.evidence,
    )

    if assessment.all_satisfied:
        return "completed"
    if output.status == "blocked":
        return "blocked"
    if output.status == "failed":
        return "failed"
    return "pending"
```

## 二十、控制 Replan

Replan 必须通过显式触发器：

```python
class ReplanRequest(BaseModel):
    trigger: Literal[
        "new_fact",
        "subgoal_failed",
        "subgoal_blocked",
        "tool_unavailable",
        "budget_changed",
        "goal_already_satisfied",
    ]
    evidence: list[str]
    proposed_changes: list[PlanChange]
```

Controller 比较新旧计划：

```python
def validate_replan(old_plan, new_plan, state):
    diff = compare_plans(old_plan, new_plan)

    if diff.changes_goal:
        return require_user_confirmation()
    if diff.expands_scope:
        return require_user_confirmation()
    if diff.increases_risk:
        return require_approval()
    if diff.added_tools - state.allowed_tools:
        return reject("tool_not_allowed")
    if diff.changes_success_criteria:
        return reject("planner_cannot_change_success_criteria")

    return approve_new_plan_version()
```

新版本必须保留：

- 已完成 Subgoal 和完成证据；
- 已发生的外部副作用及幂等记录；
- 已确认事实和 Artifact；
- 当前预算消耗、错误和审批结果；
- `version`、`supersedes`、`revision_reason` 和 Plan diff。

## 二十一、三种 Plan 控制模式

| 模式 | 实现方式 | 控制性 | 适用场景 |
| --- | --- | --- | --- |
| 固定模板 | 预定义 Subgoal、依赖和顺序，模型只填参数 | 最高 | 审批、交易和高风险流程 |
| 模板 + 受限动态规划 | 程序定义允许的 Subgoal 类型和图骨架，模型在范围内组合 | 高 | 大多数生产 Agent |
| 完全动态规划 | 模型自由生成 Subgoal 和依赖，程序做最终校验 | 较低 | 低风险研究和开放探索 |

推荐默认方式：

> **固定能力和安全边界，动态选择执行路线。**

## 二十二、Plan Controller 最小骨架

```python
class PlanController:
    def create(self, goal, state) -> Plan:
        planner_input = self.build_planner_input(goal, state)
        proposal = self.planner.propose(planner_input)
        self.validate_plan(proposal, state)
        return self.activate(proposal, state)

    def next_subgoal(self, state) -> SubGoal:
        ready = self.get_ready_subgoals(state.current_plan)
        return self.scheduler.select(ready, state)

    def build_input(self, subgoal, state) -> SubGoalInput:
        return self.context_builder.build(subgoal, state)

    def accept_output(self, subgoal, output, state):
        self.validate_output(subgoal, output, state)
        assessment = self.evaluator.evaluate(
            subgoal,
            output,
            state,
        )
        self.update_state(assessment, state)

    def replan(self, request, state) -> Plan:
        proposal = self.planner.replan(request, state)
        self.validate_replan(
            state.current_plan,
            proposal,
            state,
        )
        return self.activate_new_version(proposal, state)
```

Plan Controller 的控制面可以归纳为：

| 控制范围 | 主要机制 |
| --- | --- |
| Plan 创建 | PlannerInput、模板、允许的 Subgoal 类型 |
| Plan 输出 | Plan Schema、依赖校验、风险和预算策略 |
| Plan 执行 | 状态机、Scheduler、权限、步数和审批 |
| Subgoal 输入 | Context Builder、数据范围、工具交集和执行限制 |
| Subgoal 输出 | Output Schema、Evidence、Artifact 和副作用凭证 |
| Replan | Trigger、Plan Diff、Replan Gate 和版本记录 |

# 第四部分：检查与边界

## 二十三、设计检查清单

### Goal Intake

- [ ] 用户是否只需表达自然目标，而不是填写内部执行规格？
- [ ] 自动补全字段是否记录来源、置信度和关键假设？
- [ ] 是否优先使用安全默认值、页面上下文或只读工具补全信息？
- [ ] 是否只在高影响且无法安全推断的信息上询问用户？
- [ ] Goal 是否包含目标、范围、约束、交付物和成功标准？

### Plan

- [ ] Goal 与 Plan 是否分开存储和版本化？
- [ ] 子目标是否描述可验证结果，而不是预设工具调用？
- [ ] 每个 Subgoal 是否有依赖、完成标准、权限和状态？
- [ ] 每次 Replan 是否记录原因、旧版本和替代关系？
- [ ] Replan Gate 是否阻止范围扩大、权限提升和成功标准被静默修改？
- [ ] Goal 已完成时，是否会取消不再需要的剩余步骤？

### Plan Controller

- [ ] Planner 是否只能看到最小且可信的 PlannerInput？
- [ ] PlanProposal 是否经过依赖、权限、风险和预算校验后才激活？
- [ ] 生命周期状态是否只能由 Controller 修改？
- [ ] Scheduler 是否只能选择依赖已经完成的 Ready Subgoal？
- [ ] Subgoal 输入输出是否有独立 Schema 和数据权限范围？
- [ ] Executor 的 `candidate_completed` 是否还会经过完成证据校验？
- [ ] Replan 是否经过 Plan Diff 和 Replan Gate？

## 二十四、常见误区

| 误区 | 正确认识 |
| --- | --- |
| 用户必须填写完整 Goal | 用户表达自然意图，系统负责规范化和策略补全 |
| Goal 和 Plan 是一个对象 | Goal 定义终点，Plan 定义当前路线，应独立版本化 |
| 子目标就是工具调用 | 子目标描述局部结果，工具只是实现它的一种方式 |
| Plan 越详细越可靠 | 远期计划应保持粗粒度，近期根据观察滚动细化 |
| Planner 可以自由调整 Goal | Planner 只能在既有 Goal 与权限边界内调整路线 |
| Plan 执行完成等于任务成功 | 成功由 Goal 的成功标准和证据判断 |
| Planner 生成后可以直接执行 | Planner 只生成 PlanProposal，校验并批准后才能成为 Active Plan |
| Executor 说完成就代表完成 | `candidate_completed` 必须经过证据和 Completion Criteria 校验 |
| Replan 可以顺便增加工具和权限 | 新工具、范围扩大和风险提升必须拒绝或重新授权 |

## 二十五、理解检查

1. User Intent、Goal、Plan、Subgoal、Loop 和 Action 分别回答什么问题？
2. 哪些信息可以自动默认或发现，哪些必须询问用户？
3. 为什么 Plan 应由 Goal 与当前 State 共同派生？
4. 什么变化属于 Replan，什么变化已经构成 Goal 变更？
5. 为什么子目标应该有完成证据，而不能只记录 `completed=true`？
6. 为什么计划中的步骤全部执行完，任务仍可能失败？
7. PlannerInput 应该包含什么，又应该排除什么？
8. PlanProposal 与 Active Plan 有什么区别？
9. 为什么 Scheduler 只能从 Ready Subgoal 中选择？
10. 为什么 Executor 的输出不能直接写入 State？
11. Plan Diff 和 Replan Gate 分别解决什么问题？

## 结语

Goal 与 Plan 的分离，是 Agent 从“会列步骤”走向“能够可靠完成任务”的基础。Goal 提供稳定的目的地和边界，Plan 提供可调整的路线，Subgoal 提供可验证的局部结果，Loop 通过真实环境反馈完成当前 Subgoal，而 Plan Controller 负责确保整个创建、执行、输入输出和重规划过程始终处于应用可控制的范围内。
