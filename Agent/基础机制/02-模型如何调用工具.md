## 一、一次调用的最小契约

应用提供本轮 Context、可用工具的名称/描述/参数 Schema、期望的输出结构和预算；模型返回文本或一个候选动作。应用解析、校验、执行，再把结果作为新观察送回下一轮。模型“调用工具”通常是提出带参数的请求，真实副作用由应用的工具执行器产生。

```text
Context + 允许工具 → 模型候选输出 → 解析/Schema 校验
  → 身份与业务规则校验 → 执行工具 → 记录结果/错误 → 下一轮
```

## 二、结构化输出保证什么、不保证什么

Schema 可约束字段、类型和枚举，减少解析歧义；它不能证明事实正确、用户有权限、参数在业务上有效。比如 `{ "action": "read_logs", "service": "orders" }` 格式合法，仍须检查调用者能否读取该服务、时间范围是否合理。解析失败应有明确的修复、重试或停止路径，不应静默改成默认动作。

工具返回也需要稳定的成功/失败结构：错误类别、是否可重试、结果引用和观察时间。超时不等于工具没有执行；对写操作要先查实际状态，再决定重试。

## 三、流式输出与最终状态

流式片段适合展示进度，但片段可能尚未完整或最终被校验拒绝。UI 可以展示“正在分析”或增量草稿，业务 State 和副作用应以完整、校验后的动作或结果为准。网络中断时以运行 ID 和持久状态恢复，不能仅凭最后看到的流片段推断任务已完成。

## 四、模型选择与降级

选模型先列任务需要的能力：语言理解、结构化输出、工具使用、上下文长度、延迟与成本约束。用同一评测集验证候选模型和 Prompt；更换模型后重新检查解析失败、工具选择和安全边界。降级模型或重试可能改变行为，必须记录其版本和触发原因；任务无法安全完成时给出清楚的失败状态。

**练习：**为只读诊断定义 `call_tool | respond | ask_user | stop` 四种动作，分别测试合法调用、缺必填参数、请求写工具、工具超时。检查 Schema 与应用权限校验各拦住了什么。

## 五、完整例子：一次日志查询如何完成

用户要求“只读诊断订单接口最近十分钟的延迟”。应用只提供日志查询工具，输入契约要求 `service` 为授权服务名、`minutes` 为 1～30 的整数。下面使用框架无关结构；真实 SDK 字段可能不同。

```json
{
  "action": "call_tool",
  "tool": "read_logs",
  "arguments": {"service": "orders", "minutes": 10}
}
```

1. 应用解析输出，验证动作枚举、工具名称及参数类型；`minutes: "很多"` 应校验失败。
2. 工具执行器根据调用者身份检查是否允许读取 `orders`，并校验时间范围；合法 JSON 不意味着有权限。
3. 执行成功时返回结构化观察及来源，例如 `{"source":"logs:query-17","events":["pool exhausted"]}`。
4. 应用保留来源，把必要结果作为外部数据加入下一轮 Context。模型决定继续查指标或回答；“查到一条日志”尚不是最终任务成功。
5. 若超时，返回明确的错误状态。只读查询可按预算有限重试；有副作用的工具则先核对外部状态。

**常见错误：**把候选调用直接拼接成 shell/SQL；把 Schema 验证当业务授权；流式参数尚未完整便执行动作；把工具错误字符串当成功结果继续推理。

**自检：**模型返回未授权服务名、错误参数类型、未知工具名时，分别由哪一层拒绝？这些拒绝能否进入下一轮反馈，而不泄露敏感信息？
